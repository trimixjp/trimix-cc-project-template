# エージェント定義ファイル記述ガイドライン

`.claude/` 配下のエージェント定義・DOD・コマンドファイルを一貫したスタイルで記述するためのガイドラインです。

---

## 1. このガイドラインの目的

AIエージェントはこれらのファイルを読んで動作します。記述スタイルが統一されていないと、エージェントが誤読・誤動作する原因になります。このガイドラインは以下を目的とします。

- エージェント定義ファイルの構成・記述スタイルを統一する
- 新規ファイル作成時の迷いをなくす
- レビュー時の基準を明確にする

---

## 2. エージェント定義ファイルの標準構成

### 2-1. ファイル配置ルール

| ファイル種別 | 配置場所 |
|-------------|---------|
| チーム専用エージェント | `.claude/teams/<チーム名>/agents/<エージェント名>.md` |
| チーム横断エージェント | `.claude/agents/<エージェント名>.md` |

### 2-2. 標準テンプレート

```markdown
---
```

### 2-3. セクションの必須・任意

| セクション | 必須 / 任意 | 説明 |
|-----------|------------|------|
| フロントマター（`---`）| 必須 | `name`・`description` を含む |
| `## 役割` | 必須 | 1〜3 文で簡潔に |
| `## 起動条件` | 必須 | 番号付きリストで列挙 |
| `## 動作フロー` | 必須 | ステップ形式で記述 |
| `## チケットコメントフォーマット` | 必須 | コードブロックで定義 |
| `## エスカレーション条件` | 必須 | **省略禁止**（Human-Escalator 自身を除く） |
| `## 失敗時挙動` | 必須 | 失敗ケースの分岐を最低1つ定義する（9-5 参照） |
| `## 完了条件（exit criteria）` | 必須 | 検証可能なチェックリスト（9-1 参照） |
| `## 状態記録の原則` | 必須 | 強制力文を含める（9-2 参照） |
| `## 重要な原則` | 必須 | 最低1項目 |
| その他のセクション | 任意 | エージェント固有の情報（担当領域テーブル等） |

## 3. 各セクションの記述ルール

### 3-1. フロントマター

```yaml
---
name: editor-in-chief           # kebab-case で統一
description: コンテンツチームのリーダーAI。要件分析・方針決定・チーム全体の進行管理を担う編集長
---
```

**ルール:**
- `name` は `.md` のファイル名（拡張子なし）と一致させる
- `description` は「チーム名 + 役職 + 主な責務」を一行に収める
- 特殊なモデルを使用する場合は `model: opus` 等のエイリアスで追加する（バージョン固定は禁止。詳細は「3-8. モデル指定ガイドライン」を参照）

### 3-2. 役割セクション

```markdown
## 役割

Implementer はバックエンドチームの「実装担当AI」です。Tech-Lead が決定した設計方針に従いコードを実装します。
```

**ルール:**
- `<エージェント名> は <チーム名>チームの「<役職>AI」です。` の形式で開始する
- 1〜3 文以内にまとめる
- 自律的に起動しない（依頼受けのみの）エージェントは `**〇〇から依頼を受けた場合のみ起動します。**` を明記する

### 3-3. 起動条件セクション

```markdown
## 起動条件

以下のいずれかを満たした時点で起動します。

1. `backend:implementer` ラベルが付与された チケットが作成・更新された
2. Reviewer からの差し戻しにより `backend:implementer` ラベルが再付与された
```

**ルール:**
- 番号付きリストで記述する
- 条件が1つだけでも番号付きリストを使用する
- ラベル名は バッククォートで囲む
- 「依頼受けのみ」エージェントは「**〇〇が依頼した場合のみ起動します。** 自律的には起動しません。」と明記する

### 3-4. 動作フローセクション

```markdown
## 動作フロー

### ステップ1: インシデント確認

`.claude/incidents/index.yml` を読み込み、対象チケットに関連するインシデントがないか確認します。

### ステップ2: 要件分析

チケット本文・関連ドキュメントを読み込み、以下を確認します。

| 確認項目 | 内容 |
|----------|------|
| 機能要件 | 何を実装するか |
```

**ルール:**
- ステップは `### ステップN: <タイトル>` の形式で記述する
- 判断分岐は `**〇〇の場合:**` / `**〇〇でない場合:**` で示す
- インシデント確認ステップ（Tech-Lead・Frontend-Lead・Editor-in-Chief等のリーダー）は必ずステップ1に置く
- テーブルは `| 列1 | 列2 |` / `|-----|-----|` の形式を使用する

### 3-5. チケットコメントフォーマットセクション

```markdown
## チケットコメントフォーマット

### 設計方針コメント

\`\`\`
🔧 Tech-Lead: 設計方針を決定しました

## 参照ドキュメント
- （参照したドキュメント）

## 設計方針
（内容）

⏭️ 次のアクション: backend:implementer に引き継ぎます
\`\`\`
```

**ルール:**
- フォーマットはコードブロック（` ``` `）で囲む
- 末尾に `⏭️ 次のアクション:` で次の工程を明示する
- エモジは定型（📝=計画・設計、🔧=技術実装、✍️=執筆、✅=合格・完了、❌=不合格・差し戻し、🔬=調査）を使用する
- 完了報告には「作成・変更したファイル一覧」と「懸念点・注意事項」を含める
- 完了報告コメントには必須5フィールド（9-3）を含め、「完了条件チェック」フィールドは転記式（9-1）で記述する

### 3-6. エスカレーション条件セクション

```markdown
## エスカレーション条件

以下の場合は `human-escalator` エージェントを呼び出します。

- 法的リスク（名誉毀損・著作権・個人情報）が疑われる（`legal`）
- 費用が発生するサービスの利用が必要と判明した（`budget`）
- `.claude/escalation-rules.yml` の `escalation_triggers` に該当する事象
```

**ルール:**
- このセクションの**省略は禁止**です（省略するとエスカレーション経路が失われ、判断不能時にワークフローが停止します）
- 必ず末尾に `.claude/escalation-rules.yml` への参照を含める
  - パスは `.claude/escalation-rules.yml` を使用する（`.claude/_shared/` は誤り）
- エスカレーション種別（`legal` / `budget` / `merge_approval` / `ambiguous_spec`）を括弧書きで明示する
- Human-Escalator エージェント自身にはこのセクションは不要

### 3-7. 重要な原則セクション

```markdown
## 重要な原則

- Tech-Lead 自身はコードを書きません。実装は必ず Implementer に委譲します
- 全ての設計判断には参照仕様書またはルールファイルを明記します
- 懸念点は「未解決」として明示し、隠蔽・省略してはいけません
```

**ルール:**
- 箇条書き（`-`）で記述する
- 「〜してはいけません」という禁止事項を含める
- 3〜7項目を目安にする

### 3-8. モデル・effort 指定ガイドライン

フロントマターの `model` / `effort` / `model_role` で、エージェントが使用するモデルと推論深度を指定します。

```yaml
---
name: tech-lead
description: バックエンドチームのリーダーAI。要件分析・設計方針決定・タスク振り分けを担う
model: opus
effort: high
model_role: leader
---
```

**ルール:**
- モデルのバージョン固定（`claude-opus-4-7` 等のモデルID指定）は**禁止**です。モデルの提供終了時にエージェントが動作しなくなります
- 必ずエイリアス（`fable` / `opus` / `sonnet` / `haiku`）で指定する
- `effort` は `low` / `medium` / `high` / `xhigh` / `max`（利用可能値はモデルに依存）

**setup 時の一括設定（推奨）:**

`/ai-team-setup` で **runtime（Claude Code / Grok Build）**・性能プロファイル・effort 深度を選び、全エージェント・スキルに反映します。**再 setup で runtime を切り替え可能**です。

**Claude Code:**

| 性能プロファイル | leader | verifier | worker | simple |
|-----------------|--------|----------|--------|--------|
| ハイパフォーマンス | fable | opus | opus | sonnet |
| バランス（デフォルト） | opus | opus | sonnet | haiku |
| 低コスト | sonnet | sonnet | sonnet | haiku |

| effort 深度 | Claude effort |
|------------|---------------|
| 深く | xhigh |
| 普通（デフォルト） | high |
| 軽く | medium |

**Grok Build:**

| 性能プロファイル | leader | verifier | worker | simple |
|-----------------|--------|----------|--------|--------|
| ハイパフォーマンス / バランス | grok-4.5 | grok-4.5 | grok-4.5 | grok-composer-2.5-fast |
| 低コスト | grok-composer-2.5-fast | grok-composer-2.5-fast | grok-composer-2.5-fast | grok-composer-2.5-fast |

| effort 深度 | Grok effort |
|------------|-------------|
| 深く / 普通 | high |
| 軽く | medium |

Grok 選択時は `.grok/agents/` と `.grok/commands/` にもミラーされます。

役割の例:
- **leader**: dispatcher, contributor, tech-lead, frontend-lead, editor-in-chief, infra-lead, architect, strategist, director 等。**次の担当へ渡す チケットコメントには詳細な設計書（要件・方針・タスク分割・制約・完了条件）を書く**
- **verifier**: reviewer, reviewer-a, reviewer-b, security-engineer, compliance, render-reviewer, script-qa などの *-qa 等。他者の成果物の合否判定を専任で行う（自分では制作しない）
- **worker**: implementer, developer, writer, researcher 等。リーダーの設計に従って実装・調査する
- **simple**: pr-creator, version-bumper, tech-writer, publisher, editor（レンダ）等

**細かい設定は md ファイルの変更で可能です。** 個別にモデルだけ変えたい場合は、対象 md の `model` / `effort` を直接編集してください。プロファイルの一括再適用:

```bash
node <パッケージルート>/bin/lib/apply-model-profile.js \
  --runtime claude-code --profile balance --effort normal --dir .claude
# Grok に切替:
node <パッケージルート>/bin/lib/apply-model-profile.js \
  --runtime grok --profile balance --effort normal --dir .claude
```

定義の詳細は `.claude/model-profiles.yml` および `bin/lib/model-profiles.js` を参照してください。

## 4. DODファイルの記述ルール

### 4-1. ファイル配置ルール

```
.claude/teams/<チーム名>/dod/<タスクタイプ>.md
```

### 4-2. 標準テンプレート

```markdown
# DOD（Definition of Done）— <タスクタイプ名>

> **対象**: <このDODが適用される作業の説明>
> **Contributor がクローズ前にこのチェックリストで完了を判断します**

---

## ✅ <フェーズ名>

- [ ] <検証可能な完了条件>
  - <条件を満たすために確認すべきこと>

## ✅ <フェーズ名>

- [ ] <検証可能な完了条件>

---

**完了判定**: 上記すべての項目が ✅ であることを Contributor が確認してから チケットをクローズします。
```

### 4-3. チェックリスト項目の書き方

**良い例（検証可能）:**
```
- [ ] Reviewer によるレビューが完了し「合格」コメントがある
- [ ] CRITICAL 件数: 0件（または全件対応済みで再レビュー「合格」あり）
- [ ] 変更ファイル一覧が Implementer のコメントに列挙されている
```

**悪い例（曖昧・検証不能）:**
```
- [ ] コードの品質が高い
- [ ] 適切にレビューされた
- [ ] ドキュメントが更新された
```

**ルール:**
- チェック条件は「誰が・何を・どこで確認するか」が明確になっている
- 「合格」「完了」の判定基準を具体的に記述する（例: 「合格コメントがある」「件数が0件」）
- 条件が複数の場合は箇条書きでネストする
- 対象外の場合は `（なければ「対象外」）` と補足する

## 5. コマンド定義ファイルの記述ルール

### 5-1. ファイル配置ルール

```
.claude/commands/<コマンド名>.md
```

### 5-2. フロントマター

スキル（コマンド）定義もエージェントと同様に `model` / `effort` / `model_role` を明示します。

```yaml
---
name: ai-team-run
description: チケット（GitHub / ローカル md / Jira等）を読み込み、AIチームのワークフローを起動します。引数にチケットのURLまたはIDを指定してください。
model: opus
effort: high
model_role: leader
---
```

| frontmatter | 意味 |
|-------------|------|
| `name` | コマンド名（スラッシュなし） |
| `description` | ユーザー向けの説明（`/ai-team-gallery` 等で表示される） |
| `model` | 実行モデルのエイリアス（runtime 依存。バージョン固定 ID は禁止） |
| `effort` | 推論深度（`low` / `medium` / `high` / `xhigh` / `max`） |
| `model_role` | プロファイル適用時の役割（`leader` / `verifier` / `worker` / `simple`） |

**ルール:**
- `name` はコマンド名（スラッシュなし）
- `description` はユーザー向けの説明（`/ai-team-gallery` 等で表示される）
- `model` / `effort` / `model_role` はエージェント定義と同じ規約に従う（詳細は「3-8. モデル・effort 指定ガイドライン」）
- `/ai-team-setup` の runtime・性能プロファイル・effort 深度で全スキルへ一括反映される（個別上書き可）

### 5-3. 本文の記述

- コマンドの引数・オプションを冒頭に記述する
- ステップは `## ステップN: <タイトル>` で記述する
- ツール呼び出しはコードブロックで示す
- 条件分岐は箇条書きまたはテーブルで明示する

## 6. エスカレーション条件の書き方

### 6-1. 参照するファイル

エスカレーション条件は必ず `.claude/escalation-rules.yml` を参照します。

```markdown
## エスカレーション条件

以下の場合は `human-escalator` エージェントを呼び出します。

- <具体的な条件>（`<種別>`）
- `.claude/escalation-rules.yml` の `escalation_triggers` に該当する事象
```

### 6-2. エスカレーション種別

| 種別 | 用途 |
|------|------|
| `legal` | 法的判断・著作権・個人情報・契約に関わる事象 |
| `budget` | 費用が発生するサービス利用・予算承認を必要とする事象 |
| `merge_approval` | プルリクエストの承認・main ブランチへのマージ |
| `ambiguous_spec` | ルール・仕様書・CLAUDE.md に記述がなく、判断できない事象 |

### 6-3. 誤ったパス参照（禁止）

```markdown
# 誤り（_shared/ は存在しない）
- `.claude/_shared/escalation-rules.yml` の `escalation_triggers` に該当する事象

# 正しい
- `.claude/escalation-rules.yml` の `escalation_triggers` に該当する事象
```

## 7. 禁止事項・アンチパターン

### 7-1. フロントマターの省略

```markdown
# 悪い例（フロントマターなし）
# Writer - コンテンツチーム執筆担当

# 良い例
---
name: writer
description: コンテンツチームの執筆担当AI。Editor-in-Chiefの方針に従いコンテンツを作成・編集する
---

# Writer - コンテンツチーム執筆担当
```

### 7-2. 曖昧な完了条件

```markdown
# 悪い例（確認方法が不明）
- [ ] コンテンツが適切である

# 良い例（具体的で検証可能）
- [ ] Compliance によるチェックが完了し「合格」コメントがある
```

### 7-3. エスカレーション条件のパス誤記

```markdown
# 禁止
`.claude/_shared/escalation-rules.yml`

# 正しい
`.claude/escalation-rules.yml`
```

### 7-4. 役割と実装の混在

エージェント定義ファイルにはエージェントの「振る舞い」を記述します。実際のコード・設定値・業務ルールの詳細を直接埋め込まないでください。詳細は別ファイルへの参照として示します。

### 7-5. セクションの順序の乱れ

セクションは常に以下の順序で記述します。
1. フロントマター
2. `# タイトル`
3. `## 役割`
4. `## 起動条件`
5. `## 動作フロー`
6. `## チケットコメントフォーマット`
7. `## エスカレーション条件`
8. `## 失敗時挙動`
9. `## 完了条件（exit criteria）`
10. `## 状態記録の原則`
11. `## 重要な原則`

---

## 8. チェックリスト

### 新規作成時

- [ ] フロントマターに `name`・`description` が存在する
- [ ] `name` がファイル名（拡張子なし）と一致している
- [ ] 標準セクションが全て揃っている（役割・起動条件・動作フロー・フォーマット・エスカレーション・失敗時挙動・完了条件・状態記録・原則）
- [ ] エスカレーション条件のパスが `.claude/escalation-rules.yml` になっている
- [ ] エスカレーション種別（`legal` / `budget` 等）が括弧書きで明示されている
- [ ] コメントフォーマットに `⏭️ 次のアクション:` が含まれている
- [ ] コメントフォーマットの「完了条件チェック」が転記式（9-1）になっている（単一チェック箱は禁止）
- [ ] 完了条件（exit criteria）に「必須5フィールドを記載した」の検証項目がある（9-3）
- [ ] 「失敗時挙動」に失敗ケースの分岐が最低1つ定義されている（9-5）
- [ ] 検証指示に具体的コマンド・ツール名・合格基準が併記されている（9-6）
- [ ] 高推論モデル前提の曖昧な記述（「文脈から判断」「適切に対応」等）がない（9-7）
- [ ] 設定値（`base_branch`・`rework_limit` 等）が直書きされず config 参照になっている（9-8）
- [ ] 「重要な原則」に禁止事項が含まれている

### レビュー時

- [ ] セクションの順序が標準構成に従っている
- [ ] フロントマターの `name` とファイル名が一致している
- [ ] エスカレーション条件の参照パスが正しい（`_shared/` が含まれていない）
- [ ] 動作フローのステップが番号付きで記述されている
- [ ] DODのチェックリスト項目が検証可能な具体的条件になっている
- [ ] 機能的な変更（エージェントの振る舞い変更）が含まれていないか確認する

## 9. 統一規約の書き方ガイド

全エージェントに共通する規約（完了条件・状態記録・コメントフィールド）をエージェント定義に記述する際のガイドです。

### 9-1. 完了条件（exit criteria）チェックリスト

各エージェントの動作フローの末尾に、そのステップを「完了」とみなす条件をチェックリストで明記します。

```markdown
## 完了条件（exit criteria）

- [ ] 設計方針コメントを チケットに投稿した
- [ ] 参照したルール・仕様書を方針コメントに明記した
- [ ] 次のステップのラベル（`backend:implementer`）を付与した
```

**ルール:**
- DODと同様、「誰が・何を・どこで確認するか」が明確な検証可能条件で書く
- 完了報告コメントの「完了条件チェック」フィールドで、このチェックリストの充足状況を報告する
- 1つでも未充足の項目がある状態で次のステップへ引き継いではいけません

**完了条件チェックの転記式（必須）:**

コメント雛形の「完了条件チェック」フィールドは、必ず次の転記式で記述します。

```markdown
## 完了条件チェック
- [x] （「完了条件（exit criteria）」の各項目を転記してチェック）
```

「完了条件の全項目を確認済み」のような**単一チェック箱は禁止**です（項目ごとの検証が省略され、未充足の見落としを機械的に検出できなくなるため）。

### 9-2. 状態記録の原則

- ワークフローの状態は **チケットのラベルとコメントのみ**で表現する（エージェントの内部状態・会話コンテキストに依存しない）
- セッションが中断しても `/ai-team-resume` が**コメント履歴のみ**で状態を復元し、続きから再開できる状態を常に保つ
- 判断・分岐を行った場合は、その根拠と参照ドキュメントを必ずコメントに残す
- 各エージェント定義の「状態記録の原則」セクションには、次の一文を必ず含める（省略禁止）:
  **「コメントに記録されていない作業・判断は存在しないものとして扱われます」**

### 9-3. コメント必須5フィールド

各エージェントの完了報告コメントには、以下の5フィールドを必ず含めます。

| フィールド | 内容 |
|-----------|------|
| 実施内容 | このステップで何を行ったか |
| 成果物 | 作成・変更したファイル・PR・コメント等の一覧 |
| 判断根拠 | 分岐・選択を行った理由と参照したルール・ドキュメント |
| 完了条件チェック | 完了条件（exit criteria）の充足状況 |
| 次のアクション | 次に起動するステップ・付与するラベル（`⏭️ 次のアクション:` 行で明示） |

**記述例:**

```
🔧 Tech-Lead: 設計方針を決定しました

## 実施内容
要件分析・インシデント確認・設計方針の決定を行いました。

## 成果物
- 設計方針コメント（本コメント）

## 判断根拠
- `.claude/rules/security.md` の環境変数ルールに基づき config 参照方式を採用

## 完了条件チェック
- [x] 設計方針コメントを チケットに投稿した
- [x] 参照したルール・仕様書を明記した

⏭️ 次のアクション: backend:implementer に引き継ぎます
```

**ルール:**
- 「次のアクション」は既存のコメントフォーマット規約（3-5）の `⏭️ 次のアクション:` 行と兼ねてよい
- フィールドを省略・統合してはいけません（resume がコメント履歴のみで状態を復元するための前提となります）
- 各エージェントの完了条件（exit criteria）には「完了報告コメントに必須5フィールド（実施内容・成果物・判断根拠・完了条件チェック・次のアクション）を記載した」の検証項目を必ず含める

### 9-4. 差し戻しカウントの統一規約

差し戻し回数（`rework_limit` の判定）は、コメントの**先頭行のみ**を機械照合してカウントします。全チームのレビュアー定義はこの規約に従って記述してください。

**先頭行規約:**

差し戻し（不合格）コメントの先頭行は、必ず次の形式で記述します。分母は `<rework_limit>`（workflow.yml から取得コマンドで解決。値の直書き禁止＝9-8 準拠）とします。

```
❌ <エージェント名>: 差し戻し（差し戻し回数: n/<rework_limit>）
```

**カウントコマンド（先頭行のみ照合・引用による偽陽性なし）:**

```bash
# 差し戻し上限を workflow.yml から取得（rework_limit。既定: 2。値の直書き禁止＝9-8 準拠）
grep -E '^rework_limit:' .claude/teams/<team_id>/workflow.yml | awk '{print $2}'

# 過去の差し戻しコメント数を数える
gh api "repos/<owner>/<repo>/issues/<番号>/comments" --paginate \
  --jq '.[].body | split("\n")[0]' | grep -cE '^❌ .+: 差し戻し' || true
```

**ルール:**
- カウント **n < rework_limit** → 差し戻し可。カウント **n ≥ rework_limit** → 差し戻しせず `escalated:human` へ遷移する。上限値は workflow.yml の `rework_limit` が正です
- 差し戻し以外のコメント（独立レビューの暫定結果等）では、**先頭行に「差し戻し」の語を使ってはいけません**（カウントの偽陽性を防ぐため。例: 独立レビューの暫定結果は `🔍 Reviewer-A: 独立レビュー完了（暫定）` のように書く）
- 本文中での「差し戻し」への言及・引用はカウントに影響しません（先頭行のみを照合するため）
- 定義本文で上限に言及する際は必ず「workflow.yml の `rework_limit` が正」と出典を併記します（9-8 参照）
- **同一チケットに複数の差し戻しループが共存するチーム**（例: sns の Strategist→Researcher と Operator→Writer）では、カウント正規表現を必ずエージェント名でアンカーします（例: `grep -cE '^❌ Strategist: 差し戻し'`）。汎用パターン `^❌ .+: 差し戻し` のままでは他ループの差し戻しを誤カウントします

### 9-5. 「失敗時挙動」セクション（必須）

各エージェント定義に `## 失敗時挙動` セクションを設け、**コマンド失敗時・参照ファイル欠落時・ラベル不整合時**の分岐を最低1つ定義します。省略は禁止です。

**既定原則: 安全側に倒す**

- 対象範囲を広げすぎない（計測不能時に全件・全履歴を対象にしない）
- より厳格なレビュー方式を選ぶ
- 判断できない場合は停止し、経緯を チケットコメントに記録してエスカレーションする

**模範例（`frontend-lead.md`）:** 基準ブランチの存在確認（`git rev-parse --verify <base_branch>`）に失敗した場合は「計測不能」とみなし、安全側に倒して**ダブルレビュー**を選択し、その旨を判断コメントに記録する。

### 9-6. 機械的検証の原則

「動作確認」「事実確認」「影響範囲を確認」等の検証指示を書く場合は、必ず以下を併記します。主観・裁量で判定させる記述は禁止です。

- 具体的なコマンドまたはツール名（コピペで実行可能な形）
- 合格基準（閾値・期待値・判定正規表現）

```markdown
# 悪い例（主観判定）
影響範囲を確認し、大きければダブルレビューにする

# 良い例（機械計測＋合格基準）
`git diff --name-only <base_branch>...HEAD | wc -l` を実行し、
file_count_threshold（review-config.yml）以上ならダブルレビュー
```

### 9-7. モデル非依存の原則

エージェント定義は、実行モデルの推論力に依存せず同じ実行品質が出るように書きます。

- 高推論モデル前提の記述を避ける（禁止例: 「最高品質の推論を使用」「文脈から判断」「適切に対応」「よしなに処理」）
- 判断は**決定表・閾値・判定正規表現・コピペ可能な bash** に落とす（模範例: `tech-lead.md` のレビュー方式判断フロー、`version-bumper.md` の semver 判定正規表現表）
- 手順の充足は転記式チェック（9-1）で機械的に検出できる形にする

### 9-8. 設定値のハードコード禁止

`base_branch`・`rework_limit`・`file_count_threshold` 等の設定値は config ファイル（`review-config.yml` / `workflow.yml`）を正とし、エージェント定義への値の直書き（`main`・`2` 等）を禁止します。

```markdown
# 悪い例（直書き）
main との差分を確認する。差し戻しは2回まで

# 良い例（config 参照＋既定値の併記）
<base_branch>（review-config.yml の detection_procedure.base_branch）との差分を確認する。
差し戻し上限は workflow.yml の rework_limit（既定: 2）を正とする
```

コメント例等に具体値を書く場合は、必ず設定キー名を併記し「config の値が正」であることを明示します。
