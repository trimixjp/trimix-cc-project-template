# ベストプラクティス

`@trimix/ai-team` を効率よく使うための知見をまとめています。

---

## Issue の書き方

### AI が処理しやすい Issue を書く

AI エージェントは Issue のタイトル・本文・ラベルを手がかりに作業内容を判断します。以下のフォーマットを意識すると処理精度が上がります。

**推奨フォーマット**

```markdown
## 背景・目的
（なぜこの作業が必要か）

## 作業内容
（具体的に何をするか）

## 受け入れ条件
- [ ] 条件 A が満たされている
- [ ] 条件 B が満たされている

## 参考情報
- 関連 Issue: #123
- 参考ドキュメント: docs/xxx.md
```

**ポイント**

| 項目 | 良い例 | 避けるべき例 |
|------|--------|-------------|
| タイトル | `feat: ユーザー認証APIにリフレッシュトークン機能を追加` | `認証改善` |
| 受け入れ条件 | チェックボックス形式で列挙 | 「いい感じに実装」 |
| 背景 | なぜ必要かを明記 | 経緯の省略 |
| 制約 | 使用ライブラリ・禁止事項を明記 | 暗黙の前提 |

---

### ラベルを先に付ける

Issue 作成時に担当チームのリーダーラベルを設定しておくと、ワークフローが即座に特定されます。ラベルがない場合は自動判断されますが、精度が下がる場合があります。

```bash
# GitHub CLI でラベルを付けて Issue を作成
gh issue create \
  --title "feat: ユーザー認証APIを実装" \
  --label "backend:tech-lead" \
  --body "..."
```

## DOD（Definition of Done）の設計

### DOD の項目数を適切に保つ

DOD の項目が多すぎると、Contributor エージェントがすべての確認に時間がかかります。推奨は 5〜10 項目です。

| DOD の種類 | 推奨項目数 | 対象 |
|-----------|-----------|------|
| `feature.md` | 6〜10 項目 | 新機能実装 |
| `bugfix.md` | 4〜7 項目 | バグ修正 |
| `review.md` | 4〜6 項目 | コードレビュー |
| `refactor.md` | 4〜6 項目 | リファクタリング |

**良い DOD の例（バグ修正）**

```markdown
- [ ] 再現手順でバグが発生しないことを確認した
- [ ] 修正に関連するテストを追加した
- [ ] 既存テストがすべて通過する
- [ ] コードレビューで承認された
- [ ] PR がマージされた
```

---

### プロジェクトのフェーズに合わせて DOD を調整する

プロトタイプ段階と本番運用段階では求められる品質基準が異なります。`.claude/teams/<team_id>/dod/` を直接編集して、フェーズに合った内容に調整してください。

| フェーズ | DOD の方針 |
|---------|-----------|
| プロトタイプ | 動作確認・基本的なエラー処理を重視 |
| MVP | テストカバレッジ・ドキュメント整備を追加 |
| 本番運用 | セキュリティレビュー・モニタリング・ロールバック手順を追加 |

## エスカレーションルールの設計

### 過度なエスカレーションを防ぐ

`.claude/escalation-rules.yml` の `ambiguous_spec` は、判断基準が曖昧なときにエスカレーションを発動します。仕様書が充実しているほどエスカレーションは減ります。

**良いエスカレーションルールの例**

```yaml
escalation_triggers:
  - type: ambiguous_spec
    description: |
      以下をすべて検索して記述が見つからず、どちらを採用しても優劣がつかない場合:
        - .claude/rules/ 配下の .md ファイル
        - CLAUDE.md
        - docs/ 配下の仕様書
```

判断の拠り所となるドキュメント（`CLAUDE.md`・`docs/` 配下の仕様書）を充実させることが、エスカレーション頻度を下げる最善策です。

---

### エスカレーション後の応答をルール化する

同じ質問への対応は、エスカレーション後のコメントに加えて CLAUDE.md や仕様書に記録しておくと、次回から自動解決できるようになります。

```markdown
<!-- CLAUDE.md に追記する例 -->
## 技術的判断基準

- ページネーションのデフォルト件数: 20件（最大 100件）
- タイムゾーン: 常に UTC で保存し、表示時にローカル変換
```

## ワークフローの最適化

### Tech-Writer の起動コストを抑える

バックエンドワークフローではデフォルトで Tech-Writer がすべての PR 前に起動します。ドキュメント更新が不要なケース（バグ修正・設定変更のみ）では、Issue ラベルを使って条件分岐できます。

`.claude/teams/backend/workflow.yml` の `tech-writer` ステップに条件を追加することで、対象 Issue を絞り込めます（[ワークフロー定義](../reference/workflow.html) の `conditions` フィールドを参照）。

---

### インシデント記録を再発防止サイクルに組み込む

インシデントは `.claude/incidents/index.yml` に蓄積されます。以下のサイクルで活用することで、同じミスの繰り返しを防げます。

```
Issue 作成 → エージェントがインシデント確認 → 注意事項を Issue に追記
         → 実装 → 不具合発生 → インシデント記録
         → 次回 Issue でまたインシデント確認 → ...（繰り返し）
```

インシデントに `keywords` を詳しく設定しておくと、関連 Issue での検出精度が上がります。

---

### Epic タスクは Dispatcher で分解する

大きなタスクは `epic` ラベルを付けて Dispatcher に分解させると、チームをまたぐ依存関係を自動で整理できます。

```bash
# Epic Issue を作成
gh issue create \
  --title "認証システムの刷新" \
  --label "epic" \
  --body "バックエンドAPI改修・フロントエンドUI更新・インフラ設定変更を含む大規模作業"
```

Dispatcher が Sub Issue に分解し、各チームに `backend:tech-lead`・`frontend:frontend-lead` 等のラベルで割り当てます（[Dispatcher](../agents/dispatcher.html) 参照）。
