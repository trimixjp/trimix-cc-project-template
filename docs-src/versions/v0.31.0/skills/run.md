# /ai-team-run — ワークフロー起動

担当チケット（チケット・Jira・Linear 等）を読み込み、適切なチームのワークフローを起動します。

> **スキル定義**: `skills/ai-team-run.md`
> **短縮エイリアス**: `/airun`（v0.27.0 以降。`/airun 42` は `/ai-team-run 42` と同じ）

---

## 使い方

```
/ai-team-run <チケットURL または チケットID>
```

引数を省略した場合、チケットの URL またはチケット内容の貼り付けを促されます。

### 実行例

```
# チケット番号で指定
/ai-team-run 42

# チケット URL で指定
/ai-team-run https://github.com/.*/issues/42

# Jira URL で指定
/ai-team-run https://your-org.atlassian.net/browse/PROJ-123

# 引数なしで起動 → チケット内容の入力を求められる
/ai-team-run
```

---

## 書き込みの同意（v0.31.0）

チケットの作成・コメント・ラベル変更と、feature ブランチの push・PR の作成は、外部への公開に当たります。`/ai-team-run` は、**最初の書き込みの前に1回だけ**、範囲を具体的に1文で確かめます。返事を待つ間は、チケットの読み込み・チームの特定・インシデントの照合など、書き込みの要らない作業を進めます。

```
#42 のワークフローが人の判断待ち（PR の承認待ち、または escalated:human）に戻るまで、#42 へのコメント・ラベル変更と、feature ブランチの push・PR 作成を行ってよいですか
```

**決定（2026-11-22、Issue #125）と理由**: 外部への公開は、範囲を明示して同意を取ってから行います。`/ai-team-run` の起動は作業の指示であり、書き込みの同意とは読み替えません。

| 場面 | 動き |
|---|---|
| 番号・URL で起動した | チケットを読んだ直後、最初のコメントの前に聞く |
| 問題の説明（自由記述）で起動した | チケットを作る前に、タイトル・本文・ラベルの案と範囲を1文にまとめて聞く |
| 起動の指示に範囲が書いてある（例: 「#42 を PR 作成まで進めて。コメントと push も任せる」）、または直前に同じ範囲の同意を得ている | 範囲を1行で表示して進める |
| `/ai-team-watch`（ソロモード） | setup で `mode: solo` を選んだ時点の同意で代え、聞かない |
| 同意が得られない | 書き込まずに、分かったことをターミナルに示して停止する |

同意の範囲は、ワークフローが人の判断待ちに戻った時点で終わります。`/ai-team-resume` で再開するときは、改めて確かめます。同意はターミナルのやり取りで完結し、チケットにはコメントしません。

## ステップ 1: チケットの読み込み

引数の形式に応じて、自動的に取得方法を選択します。

| チケットの形式 | 取得方法 |
|---------------|---------|
| 番号のみ（例: `42`） | `gh issue view 42 --json title,body,labels,assignees,comments` |
| チケット URL | `gh issue view <番号>` で取得 |
| Jira URL | URL から番号抽出後、ユーザーに内容貼り付けを依頼 |
| その他の URL | ユーザーにチケット内容の貼り付けを依頼 |

---

## ステップ 2: 前提確認

`.claude/` ディレクトリが存在しない場合、未セットアップとして `/ai-team-setup` の実行を案内して中断します。

---

## ステップ 3: チームとワークフローの特定

チケットの**ラベル**・**タイトル**・**内容**から担当チームを判定します。ラベルが優先されます。

### ラベルによる判断（優先）

| ラベルプレフィックス | 担当チーム | ワークフロー |
|---------------------|-----------|------------|
| `backend:*` | バックエンドチーム | `.claude/teams/backend/workflow.yml` |
| `frontend:*` | フロントエンドチーム | `.claude/teams/frontend/workflow.yml` |
| `content:*` | コンテンツチーム | `.claude/teams/content/workflow.yml` |
| `infra:*` | インフラチーム | `.claude/teams/infra/workflow.yml` |
| `epic` / `dispatcher` | Dispatcher | 各チームに分解（`.claude/agents/dispatcher.md`） |
| `incident` | インシデント対応 | 緊急対応フロー |
| `escalated:human` | 人間対応待ち | ワークフロー停止中（`/ai-team-resume` で再開） |

### ラベルがない場合

タイトル・本文のキーワードを次の決定表に機械的に照合してチームを推定し、ユーザーに確認してから起動します（v0.23.0 で決定表化）。どの行にも一致しない場合はユーザーに直接質問します。

確認は、推定したチームと一致したキーワードを添えた、はい／いいえで答えられる1文で行います（v0.31.0）。例: 「#42 を backend チームで始めてよいですか（本文の『API』『DB』に一致）」。キーワード対応表には誤判定があるため、確認は省きません。

| タイトル・本文のキーワード（いずれかを含む） | 付与するラベル |
|---|---|
| 複数チームにまたがる・横断・全体 | `epic` |
| 障害・本番エラー・緊急 | `incident` |
| API・DB・サーバ・バッチ・認証・バックエンド | `backend:tech-lead` |
| 画面・UI・コンポーネント・CSS・フロントエンド | `frontend:designer` |
| インフラ・クラウド・ネットワーク・デプロイ・セキュリティ | `infra:infra-lead` |
| 記事・ドキュメント・README・文章 | `content:editor-in-chief` |
| SNS・X・Instagram・投稿文 | `sns:strategist` |
| YouTube・動画・台本・チャンネル | `youtube:director` |

## ステップ 4: インシデント確認

担当チームのワークフロー起動前に `.claude/incidents/index.yml` を読み込み、チケット内容と `keywords` を照合します。関連インシデントが見つかった場合、注意事項を チケット本文末尾またはコメントとして投稿します。

```
## ⚠️ 関連インシデント注意事項

<関連インシデントの件数と、人の判断が要る点があればその1点を1〜3行。無ければ「人の判断は不要」と書く>

<details>
<summary>詳細（エージェント向けの記録）</summary>

参照: `.claude/incidents/<ファイル名>`

⛔ やってはいけないこと
- （インシデントファイルから転記）

⚠️ 注意事項
- （インシデントファイルから転記）

</details>
```

注意事項コメントも、人の判断が要る点だけを表示し、各インシデントの詳細を `<details>` に折りたたみます（書式は [エージェントのカスタマイズ](../guide/agents.html) の「コメントの表示構成」を参照）。

## ステップ 5: ワークフローの起動

### Epic / Dispatcher の場合

`.claude/agents/dispatcher.md` を読み込み、Dispatcher エージェントとして動作します。

1. チケット内容を分析して サブチケット（またはサブタスク）に分解
2. 各チームのワークフローを並列または順次で起動

### 通常チケットの場合

チームのステップのラベルが付いていない新しいチケットは、`workflow.yml` の最初のステップに対応するエージェント定義を読み込み、そのエージェントとして動作します。

例（バックエンドチームの場合）：

```
workflow.yml の steps[0] = tech-lead-analysis
→ .claude/teams/backend/agents/tech-lead.md を読み込む
→ Tech-Lead として動作開始
```

### 途中から再開する場合（v0.31.0）

チームのステップのラベル（例: `backend:implementer`）がすでに付いているチケットは、最初のステップから始め直さず、そのステップから始めます。セッションが途中で切れた場合や、`/ai-team-watch` が再開対象を処理する場合です。始め直すと、終わったステップの作業とコメントを重ねてしまうためです。

復帰先は `/ai-team-resume` と同じ決定表で決めます（ラベルがちょうど1つならそのステップ。それ以外は最後の `⏭️ 次のアクション:` 行。どちらでも決まらなければ、候補と理由を添えて1文で確かめる）。同じラベルのステップが複数ある場合（backend の `backend:tech-lead` など）は、最後の `⏭️ 次のアクション:` 行で決めます。

始める前に、最後の `⏭️ 次のアクション:` 行と、作業ブランチの `git log --oneline <base_branch>..HEAD` で、終わった作業を確かめます。進捗の記録は今までどおりチケットのコメントと git のコミットで、進捗ファイルは作りません。

### インシデントの場合

担当チームが不明な場合は、即座に `escalated:human` ラベルを付与してよいかを1文で確かめます。

## ステップ 6: エージェントとしての動作

エージェント定義に従い、チケットを処理します。

### チケットへの記録

各エージェントの作業結果は チケットコメントとして記録されます。コメントと PR 本文は、1行目・要点1〜3行・人への依頼・`⏭️ 次のアクション:` 行だけを表示し、それ以外を `<details>` に折りたたむ構成で書きます（[エージェントのカスタマイズ](../guide/agents.html) の「コメントの表示構成」を参照）。サブエージェントへ委託するときは、この構成に従う条項を委託プロンプトに含めます。

```bash
# GitHub Issues
gh issue comment <番号> --body "..."

# その他のシステム
# コメント内容をユーザーに提示し、手動での貼り付けを案内
```

### ラベルの更新

次のエージェントへの引き継ぎ時にラベルを更新します。

```bash
gh issue edit <番号> --add-label "backend:reviewer" --remove-label "backend:implementer"
```

### ワークフローの継続

現在のエージェントの処理が完了したら、`workflow.yml` の `on_complete.next` に従って次のステップへ進みます。

### ターミナルへの報告（v0.31.0）

チケットのコメントとは別に、ターミナルで人に状況を伝えます。チケットのコメントの形は変わりません。

- ステップを始めるときと終えたときに1行で伝える（例: `#42 implementer を開始` / `#42 implementer 完了: 変更 3 ファイル、npm test 120/120`）。数値は実測したものだけを書く
- 委託したステップは、委託先の報告を受け取るたびに1行で中継する
- 停止するとき（承認待ち・エスカレーション・完了・書き込みの同意が得られない）は、わかった事・やった事・次の事を短くまとめ、人の対応が要るなら何をしてほしいかを1文で書く

### 委託するかどうか（v0.31.0）

ステップは、原則として `/ai-team-run` を実行しているセッションで「そのエージェントとして」動きます。サブエージェントへ委託するのは、次の4つのどれかに当たるときだけです。

| # | 委託する場面 | 例 |
|---|---|---|
| 1 | 並列のステップ（`next` が配列） | `reviewer-a` と `reviewer-b` |
| 2 | 大量のファイルを読んで、結論だけを受け取りたい調査 | 影響範囲の洗い出し。広い探索は Explore に任せる |
| 3 | エージェント定義の `model` が、セッションのモデルと違うステップ | balance で、opus のセッションから `model: sonnet` の implementer を動かす |
| 4 | 独立した目で見る検証役（`model_role: verifier`） | reviewer・security-engineer・各 `*-qa` |

委託するときは、エージェント定義の `model` を Agent ツールの `model` に渡し、渡したモデルを委託の記録コメントに書きます。委託プロンプトは、目的・分かっていること・作業場所（`pwd` とブランチ）・資料・手順・完了条件・出力先をタグで分けた骨組みで書き、その後ろに次の節の報告契約をそのまま入れます。

**決定（2026-11-22、Issue #125）と理由**: 委託すると、渡す文脈と受け取る報告の両方で情報が落ち、費用もかかるため、必要な場面に絞ります。ただし 1・2 だけに絞ると、役割別モデル（`model_role` ごとの `model`）がほとんど効きません。Claude Code では `.claude/teams/<team>/agents/` の定義はサブエージェントとして登録されず（登録されるのは `.claude/agents/` の共通エージェントだけ）、セッションで「そのエージェントとして動作」すると、セッションのモデルで動くためです。そこで 3・4 を加えます。3 は Claude Code の runtime を前提にしています（Grok Build ではエージェントを `.grok/agents/` にミラーします）。

## サブエージェントの無音停止検知（点呼・ウォッチドッグ）

Opus / Sonnet をオーケストレーターとして使用する場合、委託したサブエージェントが API エラー等で無音停止しても気づけない問題が発生しています（実績例: 約40分間の停止を検知できず）。この機能は、バックグラウンドプロセス（`bin/watchdog.js`）を使用して、サブエージェントの生存状態を定期的に確認します。

### 仕組みの概要

```
委託時:
  1. .claude/delegation-status/issue-<番号>/<task-slug>/ ディレクトリ作成
  2. サブエージェント起動（バックグラウンド）
  3. 同時に watchdog も起動（バックグラウンド）

watchdog 監視中:
  - heartbeat.log の更新時刻を定期確認（5分間隔での更新を期待）
  - done マーカーファイルの作成を検知

停止検知時（heartbeat 10分間以上未更新）:
  - heartbeat と成果物ファイルの mtime を実測確認（長考中を誤判定しないため）
  - 生存なら → 監視継続
  - 死亡なら → 同一プロンプトで再委託（上限2回）
  - 再委託上限超過 → escalated:human へエスカレーション
```

### 設定

`.claude/ai-team-config.yml` に `delegation_watchdog` キーがある場合は下記の値で、ない場合は既定値を使用します：

```yaml
delegation_watchdog:
  stall_threshold_minutes: 10   # heartbeat 更新なし期間の閾値（既定: 10分）
  max_redelegations: 2          # 再委託の上限回数（既定: 2回）
```

### サブエージェント側の報告義務

サブエージェントには以下の報告契約を明示してください：

1. 着手時・主要ステップ完了ごと・失敗時・完了時に報告する
2. 最低5分に1回、`date '+%Y-%m-%dT%H:%M:%S' >> <heartbeat.log>` を実行する
3. 完了時に `<done マーカー>` ファイルを作成してから終了する
4. STATUS? 受信時は、3行以内+実測値付きで即応する
5. 指示で明示されたパス以外に出力・削除をしない

## ワークフロー停止条件

以下のいずれかに該当した場合、ワークフローを停止してユーザーに状況を報告します。

| 停止理由 | 対応方法 |
|---------|---------|
| `escalated:human` ラベル付与 | 人間が判断・コメント → `/ai-team-resume` で再開 |
| PR の承認・マージが必要 | 人間が承認・マージ → ワークフロー継続。人が範囲を明示して代行を任せた場合だけ、マージ条件を実測してから代行する（[エスカレーションルール](../reference/escalation.html) の `merge_approval`） |
| 重大セキュリティリスク発見 | 人間の判断・対応 → 修正後に再開 |
| `escalation-rules.yml` の `escalation_triggers` に該当 | 人間の判断 → `/ai-team-resume` |
| チケットがクローズされた | Contributor が完了処理済み → 停止 |
| 書き込みの同意が得られない | 分かったことをターミナルに示して停止（v0.31.0） |

## エージェント間の引き継ぎフロー（バックエンド例）

```
[/ai-team-run 42]
       │
       ▼
[ラベル backend:tech-lead を確認]
       │
       ▼
[tech-lead エージェント起動]
  → 要件分析・設計方針コメント投稿
  → ラベルを backend:implementer に更新
       │
       ▼
[implementer エージェント起動]
  → 実装・テスト・完了報告コメント投稿
  → ラベルを backend:tech-lead に戻す
       │
       ▼
[tech-lead がレビュー方式判断]
  → シングル or ダブルレビューを決定
  → ラベルを reviewer または reviewer-a + reviewer-b に更新
       │
       ▼
[reviewer / cross-review 完了]
  → 合格コメント投稿
  → ラベルを backend:tech-writer に更新
       │
       ▼
[tech-writer がドキュメント更新]
  → docs-src/ を更新、build.js 実行
  → ラベルを backend:pr-creator に更新
       │
       ▼
[pr-creator が PR 作成]
  → escalated:human ラベル付与
  → 人間の承認・マージを待つ
       │
       ▼
[人間がマージ後]
  → /ai-team-resume または solo 自動再開
  → contributor が DOD 確認・チケットクローズ
```
