# v0.31.0 の変更点

## 概要

v0.31.0 では、`/ai-team-run` と、そこから呼ばれるエージェント定義を、次の 3 つの考え方に合わせて見直しました。

1. 委託を必要な場面に絞り、委託するときは目的・作業場所・完了条件・モデルを渡す
2. 承認が要る操作と、人にしか決められない選択のときだけ止まる。確認は具体的な1文にする
3. 途中で切れても続きから再開でき、テストを黙って減らさない

コメントの1行目（差し戻し回数の照合）と `⏭️ 次のアクション:` 行（`/ai-team-resume` の再開処理）の決まりは変えていません。

## 決定（2026-11-22、Issue #125）

### 書き込みの同意

`/ai-team-run` は、最初の書き込みの前に1回だけ、書き込みの範囲を具体的に1文で確かめます。例: 「#42 のワークフローが人の判断待ち（PR の承認待ち、または escalated:human）に戻るまで、#42 へのコメント・ラベル変更と、feature ブランチの push・PR 作成を行ってよいですか」。返事を待つ間は、チケットの読み込み・インシデントの照合など、書き込みの要らない作業を進めます。`/ai-team-watch`（ソロモード）は、setup で `mode: solo` を選んだ時点の同意で代え、聞きません。

**理由**: チケットの作成・コメント・ラベル変更・push・PR 作成は外部への公開で、範囲を明示して同意を取ってから行うためです。起動は作業の指示であり、書き込みの同意とは読み替えません。同意の範囲はワークフローが人の判断待ちに戻った時点で終わり、`/ai-team-resume` で再開するときは改めて確かめます。人が範囲を明示して完了まで任せた場合（マージの代行を含む）は、書き込みの同意の範囲もその完了（マージ後のコメント・ラベル変更・クローズ）まで広がります。

setup がプロジェクトの `CLAUDE.md` に書く「タスク受付ルール」も、チケットを作る前にタイトルと本文の案を見せ、1文で同意を取る形にしました。

### マージの承認

`merge_approval` の「例外なく常にエスカレーションする（AIによる自動マージは禁止）」を、「マージは人の承認を得てから行う」に書き換えました。人が範囲を明示して代行を任せた場合（例: 「このチケットを完了まで任せる」）だけ、オーケストレーターがマージ条件（最終判定 合格・テストの実行結果・`mergeable` が `MERGEABLE`）を実測してから代行し、代行したことと根拠をチケットコメントに残します。

**理由**: 「絶対しない」ではなく「承認を得てから行う」と書き、効く範囲と理由を添えるためです。以前の文は、人が範囲を明示して任せた運用と食い違っていました。

### 委託するかどうか

ステップは、原則として `/ai-team-run` を実行しているセッションで「そのエージェントとして」動きます。サブエージェントへ委託するのは、①並列のステップ ②大量の読み込みで結論だけ欲しい調査 ③エージェント定義の `model` がセッションのモデルと違うステップ ④独立した目で見る検証役（`model_role: verifier`）のときだけです。委託するときは、エージェント定義の `model` を Agent ツールの `model` に渡します。

**理由**: 委託は情報が落ち、費用もかかるため必要な場面に絞ります。ただし①②だけでは、役割別モデルがほとんど効きません。Claude Code では `.claude/teams/<team>/agents/` の定義がサブエージェントとして登録されず、セッションで「そのエージェントとして動作」するとセッションのモデルで動くためです。そこで③④を加えました（Claude Code の runtime の話です）。

## 主な変更

### `/ai-team-run`

- **書き込みの同意**: 上の決定のとおり。同意が得られない場合は、書き込まずに分かったことをターミナルに示して停止します
- **委託の判断基準と委託プロンプトの骨組み**: 委託プロンプトは、目的・分かっていること・作業場所（`pwd` とブランチ）・資料・手順・完了条件・出力先をタグで分けた骨組みで書き、その後ろに報告の契約（6 条項）をそのまま入れます。6 条項の文言は変わりません
- **途中からの再開**: ステップの完了コメント（`⏭️ 次のアクション:` 行を含むコメント）があるチケットは、最初のステップから始め直さず、チームのステップのラベルと最後の `⏭️ 次のアクション:` 行で決めたステップから始めます。新規か再開かはラベルでは判定しません（新しいチケットにも先頭ステップのラベルが付いているため）。最後の `⏭️ 次のアクション:` 行と作業ブランチの `git log` で、終わった作業を確かめてから続けます（implementer・developer も、作業ブランチがあればコミット済みのタスクを確かめてから続けます）。`/ai-team-watch` が書いていた「再開モード」は、この手順を指すことを明記しました
- **確認の聞き方**: チームの推定や既存チケットの選択などで確かめるときは、推奨と理由を添えた、はい／いいえで答えられる1文で聞きます。聞く場面は変えていません
- **CLI が失敗したとき**: リトライの前に、エラー出力から原因（認証・ネットワーク・レート制限など）を確かめ、直せるものは直します。リトライの回数は1回のままです（`/ai-team-resume`・`/ai-team-watch` も同じ）
- **ターミナルへの報告**: ステップの開始と完了を1行で伝え、停止するときは、わかった事・やった事・次の事をまとめます
- **読めない参照の置き換え**: 公開されていないファイルや、以前の規約の条番号を指していた説明を、その場で読める理由に置き換えました

### エージェント定義

- **テストを減らす変更は承認制**（backend の implementer・frontend の developer）: テストを消す・スキップする・期待値を実装に合わせて書き換えるときは、理由をコメントに書き、リーダー（Tech-Lead / Frontend-Lead）の承認を得てから行います。最終の承認はマージの承認と一緒に人が行うため、PR 本文の「承認前に知っておくこと」（`テストの削除・スキップ` 行）に件数と理由を必ず出します。レビュー観点 `test-coverage` でも確かめます
- **1つずつ実装して確かめる**: implementer・developer は着手前にテストの基準値を記録し、タスクを1つずつ実装して確かめてから進みます。完了報告に「着手前の基準値」の欄を足しました
- **委託の作業台帳の片付け**（contributor）: クローズ時に `.claude/delegation-status/issue-<番号>/` を、すべてのタスクに `done` があることを確かめてから消します。setup は `.claude/delegation-status/` を `.gitignore` に冪等に追記します
- **human-merge-approval の説明**（backend・frontend の `workflow.yml`）: マージの承認の決定に合わせました。ステップの構成とラベルは変わりません

### ガイド

- エージェント記述ガイド（`.claude/docs/agent-writing-guide.md`）の「重要な原則」の規則で、禁止事項には効く範囲と理由を添え、人の承認で許されるものは「承認を得てから行う」と書くことにしました
- ワークフローガイド（`.claude/docs/workflow-guide.md`）に、3 つの決定を結論・理由・日付で記録しました

## 既存環境への影響

**破壊的変更はありません**。ワークフローのステップ構成・ラベル・コメントの1行目と `⏭️ 次のアクション:` 行は変わりません。動きが変わるのは、起動時に同意の1問が増えること、ステップの完了コメントがあるチケットが途中から始まること、ターミナルの表示が増えることです。

`upgrade` で、変更のあったスキル・共通エージェント・エスカレーションルール・導入済みのチームのファイルが更新されます。プロジェクトの `CLAUDE.md` の「タスク受付ルール」と `.gitignore` は `upgrade` の対象外です。詳しくは [移行ガイド](guide/migration.html) を参照してください。
