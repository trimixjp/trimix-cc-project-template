# アップグレード

`@trimix/ai-team` を新しいバージョンへ更新したとき、導入先プロジェクトの `.claude/` 配下に配置済みのテンプレート（エージェント定義・ワークフロー・DOD など）を最新版へ追随させるための **`upgrade` コマンド**を解説します。v0.24.0 で新設されました。

---

## なぜ `upgrade` が必要なのか

`npm install`（パッケージの更新）だけでは、更新されるのは **スキル（`.claude/commands/`）と同梱マニュアル（`ai-team-manual/`）のみ**です。`postinstall` はこの 2 つしか展開しません。

つまり、次のものは `npm install` では**一度配置されたら古いまま**になります。

| 領域 | 配置先 | `npm install` で更新 | `upgrade` で更新 |
|------|--------|:---:|:---:|
| スキル（スラッシュコマンド） | `.claude/commands/` | ✅ | ✅ |
| 同梱マニュアル | `ai-team-manual/` | ✅ | — |
| 共通エージェント | `.claude/agents/` | ❌ | ✅ |
| チームのエージェント | `.claude/teams/<team>/agents/` | ❌ | ✅ |
| ワークフロー定義 | `.claude/teams/<team>/workflow.yml` | ❌ | ✅ |
| DOD テンプレート | `.claude/teams/<team>/dod/` | ❌ | ✅ |
| レビュー判定基準 | `.claude/teams/<team>/review-config.yml` | ❌ | ✅ |
| エスカレーションルール | `.claude/escalation-rules.yml` | ❌ | ✅ |
| モデルプロファイル | `.claude/model-profiles.yml` | ❌ | ✅ |

エージェントやワークフローの改善（バグ修正・新しい判定ロジックなど）を受け取るには、パッケージを更新したあとに `upgrade` を実行する必要があります。

---

## 使い方

```bash
# 導入済みの全チームを最新テンプレートへ更新
npx @trimix/ai-team upgrade

# チームを 1 つだけ更新（team_id を指定）
npx @trimix/ai-team upgrade backend
```

`team_id` を省略すると、`.claude/teams/` に配置済みのチーム（`backend` / `frontend` / `content` / `infra` / `sns` / `youtube` のうち導入済みのもの）がすべて対象になります。共通エージェント・`escalation-rules.yml`・`model-profiles.yml`・スキルは、`team_id` の指定に関わらず**常に**対象に含まれます（チーム横断の共通設定は、まとめてバージョンに追随させるほうが安全なためです）。

既定の動作は「**差分を提示 → ユーザーが確認 → バックアップ → 適用**」です。確認なしの一括上書きは行いません。

### オプション

| オプション | 動作 |
|-----------|------|
| `--dry` | 差分の提示のみを行い、**書き込みもバックアップも一切行いません**。何が変わるかを事前に確認したいときに使います |
| `--diff` | 上書き更新・保護対象のファイルについて、**変更の中身（unified diff）を表示**します。`--dry --diff` を組み合わせると「差分を見るだけ・何も書かない」最も安全な使い方になります（後述） |
| `--force` | `# customized: true` を持つカスタマイズ済みファイルも上書きします（既定では保護されます。後述） |
| `--yes` | 確認プロンプトを省略します。**非対話環境（CI・パイプ実行など）では続行に必須**です（後述） |

```bash
# まず差分だけ確認する（安全）
npx @trimix/ai-team upgrade --dry

# 変更の中身まで確認する（何も書き込まない・最も安全）
npx @trimix/ai-team upgrade --dry --diff

# カスタマイズ済みファイルも含めてすべて最新へ揃える
npx @trimix/ai-team upgrade --force

# 対話プロンプトを出さずに適用する（CI などの非対話環境）
npx @trimix/ai-team upgrade --yes
```

### 実行時の流れ

`upgrade` は次の順序で処理します。この順序は安全のために固定されており、崩れることはありません。

1. **更新対象の列挙** — 共通設定と、対象チームの `plugin.json` の `install` マップから対象ファイルを導き出します
2. **残置 `.new` の警告** — 前回書き出した `.new` が残っていれば冒頭で告知します（削除はしません。後述）
3. **差分の提示** — 各ファイルを「新規作成 / 上書き更新 / 保護のためスキップ / 変更なし」に分類して表示します（`--diff` 指定時は変更の中身も表示）
4. `--dry` ならここで終了（何も書き込みません）
5. 適用する差分が無ければ「すべて最新です」で終了
6. **ユーザーへの確認**（`--yes` 指定時は省略）
7. **バックアップの作成**（次章。失敗したら適用せず中止）
8. **適用** — 差分のあるファイルを書き込みます。保護対象は本体を維持し、最新テンプレートを `<ファイル名>.new` として書き出します
9. **モデルプロファイルの再適用** — 今回書き込んだエージェント／スキルの `model` / `effort` を、`ai-team-config.yml` の選択済みプロファイルへ復元します（後述）
10. **baseline の更新** — 実際に書き込んだファイルのハッシュを baseline に記録します（次回の自動判定に使う）
11. **結果表示** — 更新件数・保護スキップ件数・変更なし件数・プロファイル再適用件数を表示します

## アップグレード前の自動バックアップ

**`upgrade` は、ファイルを上書きする前に必ず既存ファイルをバックアップへ退避します。** これは、有料商材としてユーザーの成果物を失う事故を許容しないための安全策です。

### なぜバックアップするのか

後述のハッシュ照合による上書き保護は、baseline に記録があるファイルを自動的に守ります。しかし baseline がまだ確立していない状況（既存導入先へ初めて本バージョンを入れた直後など）や、`--force` で意図的に上書きする場合もあります。バックアップは、そうした隙間を埋める**最後の防衛線**として、保護判定の結果に関わらず常に機能します。実行前に次の説明が表示されます。

```
🛟 アップグレード前に、上書き対象の既存ファイルをバックアップします
   理由: カスタマイズしたエージェント定義やワークフローが上書きで失われる事故を防ぐためです。
   `# customized: true` による上書き保護は、マーカーの付いていない旧世代ファイルや
   手編集したファイルまでは守れません。そこで適用直前に必ず退避します。
```

### 保存先と構造

バックアップはプロジェクトルート直下の **`.ai-team-backups/<YYYYMMDD-HHMMSS>/`**（実行日時のディレクトリ）に作成されます。退避時は**元の相対パスをそのまま保持**します。

```
.ai-team-backups/
└── 20260710-120000/
    ├── manifest.json                                   # 退避記録（後述）
    └── .claude/
        └── teams/
            └── backend/
                ├── workflow.yml
                └── agents/
                    └── tech-lead.md
```

`manifest.json` には、作成日時（`createdAt`）・パッケージバージョン（`packageVersion`）・退避した各ファイルのパスと **SHA-256 ハッシュ**（`files[].path` / `files[].sha256`）が記録されます。バックアップは退避後に SHA-256 を再計算して退避元と一致することを検証しており、破損・切り詰めコピーを検出できます。

> **バックアップ対象は差分の有無で絞りません。** `upgrade` が書き込む可能性のある全ファイルを退避します。差分検出にバグがあってもバックアップが漏れないよう、安全側に倒しています。

### 復元方法

退避したファイルは相対パスを保っているため、**バックアップディレクトリの `.claude` をプロジェクトルートへコピーし戻すだけ**で元に戻せます。完了後に、実際のパスを添えた復元コマンドが表示されます。

```
✅ バックアップを作成しました: /path/to/project/.ai-team-backups/20260710-120000
   退避ファイル数: 12 件
   元に戻すには（バックアップから復元）:
     cp -R /path/to/project/.ai-team-backups/20260710-120000/.claude ./
   ※ このバックアップは自動削除されません。不要になったら手動で削除してください。
```

つまり復元は次の 1 行です。

```bash
cp -R .ai-team-backups/20260710-120000/.claude ./
```

### バックアップの保持と `.gitignore`

- **バックアップは自動削除されません。** 削除の判断はあなたに委ねられます。繰り返し `upgrade` を実行すると世代が蓄積するため、不要になったら手動で `.ai-team-backups/` を削除してください
- バックアップ作成時に `.gitignore` へ `.ai-team-backups/` が冪等に追記されます（既に記載があれば何もしません）。退避したファイルが誤ってコミットされるのを防ぐためです
- `--dry` 実行時はバックアップを作成しません（書き込みが発生しないため）

### バックアップ失敗時は適用しない（fail-closed）

**バックアップが 1 ファイルでも失敗（コピー失敗・SHA-256 不一致など）した場合、`upgrade` はアップグレードを実行せず、終了コード 1 で停止します。** バックアップできない状態での上書きは決して行いません。

```
❌ バックアップに失敗したため、アップグレードを中止します: <理由>
   （fail-closed: バックアップできない状態での上書きは行いません）
```

この「fail-closed（安全側に倒して閉じる）」設計により、退避に失敗したままファイルが上書きされてデータが失われる事態を防ぎます。

## 手編集ファイルの上書き保護（ハッシュ照合）

**v0.24.0 では、あなたが手で編集したファイルを `upgrade` が自動的に保護します。** マーカー（`# customized: true`）を付ける必要はありません。判定は **ハッシュ照合（dpkg の conffile と同じ考え方）** で行います。

`install` / `/ai-team-setup` / `upgrade` など、テンプレートをプロジェクトへ配置するすべての経路は、配置した各ファイルの SHA-256 を **baseline（`.claude/.template-baseline.json`）** に記録します。`upgrade` は、この baseline と現物のハッシュを突き合わせて三方比較します。

| 現物の状態 | 判定 | 動作 |
|-----------|------|------|
| 新テンプレートと同一 | 変更なし | スキップ |
| **baseline と一致**（前回このツールが書いた内容のまま） | ユーザー未編集 | 安全に更新し、baseline を更新 |
| **baseline と不一致** | ユーザーが編集した | 🛡️ 保護し `<ファイル名>.new` を書き出す |
| **baseline に記録が無い** | 判定不能 | 🛡️ 安全側で保護（`baseline record` を案内） |
| ヘッダ5行に `# customized: true` | — | 🛡️ ハッシュに関わらず保護（後方互換） |

これにより、**製品が手編集を勧めているファイル**（セットアップ後に `model` / `effort` を直接書き換える `.claude/teams/<team>/agents/*.md` や `.claude/commands/*.md` など）も、マーカーを付けずに保護されます。保護されたファイルは、あなたの版を上書きしない代わりに、**最新テンプレートを隣に `<ファイル名>.new` として書き出します**（後述の「保護されたファイルへ最新の変更を取り込む」を参照）。

差分提示では「保護のためスキップ」に分類され、次のように表示されます。

```
  🛡️  保護のためスキップ（--force で上書き可能）:
     - .claude/teams/backend/workflow.yml
```

保護されたファイルを最新テンプレートへ揃えたい場合は、**`--force` を付けて再実行**します。`--force` を指定したときだけ、編集済み・カスタマイズ済みファイルも上書き対象になります（シンボリックリンク・ハードリンクの保護は `--force` でも無効化されません）。

### ハッシュの正規化（CRLF と末尾改行のみ・空白は削らない）

ハッシュを取る前に **次の2つだけ** を正規化します。**それ以上は正規化しません。**

1. 改行コードを LF に統一する（CRLF → LF）
2. ファイル末尾の改行の有無を揃える

**行頭・行末・行中の空白は削りません。** 空白を削ると、YAML のインデントや Markdown のコードブロックの意味が変わり、**本物の編集を見逃して上書きしてしまう**からです。誤判定するなら「編集していないのに保護する」側へ倒します。

- 改行コードだけを CRLF → LF に変えたファイル、末尾改行を足した／消しただけのファイルは、**編集していない扱いで更新**されます（Windows と macOS/Linux の間でチェックアウトしても誤って保護されません）。
- 一方、行頭にインデントを1つ足すなど**空白を変えた編集は「編集済み」として保護**されます。

### baseline が無い場合と `baseline record`

`upgrade` は、baseline に記録が無いファイルを「編集したのか、単に未記録なのか区別できない」ため、**安全側に倒して保護**します（黙って上書きはしません）。このとき、次のように案内します。

```
  ℹ️  baseline に記録が無いため安全側で保護したファイルが N 件あります:
     - .claude/teams/backend/workflow.yml
   これらを自動判定の対象にするには、編集していないことを確認のうえ
   `npx @trimix/ai-team baseline record` を実行すると、現在の配置内容を基準として記録できます。
```

`baseline record` は、**現在の配置内容を baseline として記録**します。`/ai-team-setup` の末尾でも自動的に実行されるため、通常は明示的に叩く必要はありません。

```bash
# 現在の配置内容を baseline として記録
npx @trimix/ai-team baseline record

# 記録内容を確認
npx @trimix/ai-team baseline show
```

> **`baseline record` は、既に baseline がある場合は `--force` なしで実行を拒否します。** これは、ユーザーが編集した後の状態を誤って baseline にしてしまい、保護が静かに外れる事故を防ぐためです。`baseline record` は「まだ何も編集していない」ことが分かっているセットアップ直後にだけ安全に実行できます。以降の baseline の更新は、`upgrade` が適用後に自動で行います（意図して再確立する場合のみ `--force`）。

### モデルプロファイル（`model` / `effort`）は upgrade をまたいで維持されます

`upgrade` はテンプレートを適用すると frontmatter の `model` / `effort` をテンプレート既定（`balance` / `normal`）へ戻してしまいます。そこで **`upgrade` は、テンプレート適用後に、あなたが `/ai-team-setup` で選んだモデルプロファイルを再適用します**。`.claude/ai-team-config.yml` の `runtime` / `model_performance` / `effort_depth` を読み、**今回書き込んだ**エージェント／スキルの `model` / `effort` を選択済みのプロファイルへ復元します。

つまり「テンプレートの本文（ロジック）は最新へ更新され、あなたが選んだモデル選択は維持される」という動作になります。手で個別に `model` を変えたファイルは前項のハッシュ照合で保護されるため、再適用の対象にもなりません（編集済みファイルには触れません）。

> **v0.24.0 での修正（データ損失バグ）**: 以前は、上書き保護が単一ファイル（`workflow.yml` / `review-config.yml`）にしか効いておらず、**ワイルドカードで展開されるファイル（`agents/*` や `dod/*`）は `--force` を付けなくても黙って上書きされていました**。v0.24.0 で保護判定を両方の経路に統一しました。

### `# customized: true` マーカー（後方互換）

ハッシュ照合に加えて、ファイル**先頭のヘッダ領域（先頭 5 行）**に `# customized: true` という文字列があるファイルは、**ハッシュに関わらず保護**されます。これは「このファイルは今後も自分で管理する」という宣言として機能する後方互換シグナルです（既にマーカーを付けて運用しているユーザーの意図を無視しないため）。

**本文中でマーカー文字列に言及しても保護対象にはなりません。** マーカーの付け方を本文で解説しているファイル（`/ai-team-configure` や `/ai-team-install` のスキルなど）を「カスタマイズ済み」と誤検出しないための仕様です（検出はヘッダ領域に限定）。

ファイル種別によってマーカーの置き場所が変わります。**frontmatter（先頭が `---`）を持つ `agents/*.md` では、`---` の直後の行**に置きます（`---` より前に置くと frontmatter が壊れます）。`workflow.yml` など frontmatter を持たない YAML では先頭行に置いてよいです。

```markdown
---
# customized: true
name: tech-lead
model: opus
---
```

```yaml
# customized: true
name: backend-workflow
```

### 保護されたファイルへ最新の変更を取り込む（`.new` と `--diff`）

保護されたファイルは上書きされませんが、あなたの版を保ったまま最新テンプレートの変更を取り込めるよう、**組み込みの手段が 2 つ**あります。どちらも Linux のパッケージ管理（dpkg の `.dpkg-dist`、RPM の `.rpmnew`）と同じ考え方です。

#### 1. `<ファイル名>.new`（最新テンプレートを隣に書き出す）

`upgrade` は、保護したファイルを上書きしない代わりに、**最新テンプレートを `<ファイル名>.new` として同じ場所に書き出します**。あなたの版はそのまま、最新テンプレートは `.new` として手元に残るため、両者を見比べて必要な差分を手作業で取り込めます。適用後に次のように案内されます。

```
  🛡️  保護のためスキップ（あなたの編集を維持しました）:
     - .claude/teams/backend/workflow.yml
       最新テンプレートを .claude/teams/backend/workflow.yml.new として保存しました
       差分の確認: diff .claude/teams/backend/workflow.yml .claude/teams/backend/workflow.yml.new
       取り込んだら .new は削除してください
```

**取り込みの手順**

1. あなたの版と `.new` の差分を確認する

   ```bash
   diff .claude/teams/backend/workflow.yml .claude/teams/backend/workflow.yml.new
   ```

2. 必要な変更を、あなたのファイル（`workflow.yml` 側）へ手で反映する
3. 取り込みが済んだら **`.new` を手動で削除する**

   ```bash
   rm .claude/teams/backend/workflow.yml.new
   ```

**`.new` は自動削除されません。** 取り込みが完了したかどうかは、あなたにしか判断できないためです。`.new` を残したまま次回 `upgrade` を実行すると、冒頭で残置が警告されます（削除は行われず、告知のみ）。

```
  ⚠️  前回の upgrade で書き出された .new が残っています（1 件）:
     - .claude/teams/backend/workflow.yml.new
   差分を取り込み済みであれば削除してください。内容が最新テンプレートと異なる .new は
   退避のうえ上書きされます（同一内容なら書き直さず、バックアップも作りません）。
```

なお、`.new` を上書きする前には**必ずバックアップへ退避**されます（前章の fail-closed と同じ扱い）。取り込み前の `.new` を誤って失うことはありません。

#### `.new` の書き出しは冪等です（再実行しても増えません）

**`.new` の書き出しは冪等**です。既に書き出した `.new` の内容が最新テンプレートと同一であれば、`upgrade` を何度繰り返しても `.new` は書き直されず、バックアップ世代（`.ai-team-backups/`）も新たに作られません。すべてのファイルが最新で、保護ファイルの `.new` も最新であれば、次のように「すべて最新です」で終了します。

```
✅ すべて最新です。適用する差分はありません。

  ℹ️  ただし保護されたファイルが 1 件あります（本体は維持。最新テンプレートは .new に保存済み）:
     - .claude/teams/backend/workflow.yml → 最新テンプレート: .claude/teams/backend/workflow.yml.new
   差分を取り込み、済んだら .new を削除してください（取り込みが未了なら未処理として残ります）。
```

これにより、`npm install` のたびに `upgrade` を回す運用でも、**同じ内容の `.new` でバックアップ世代が無限に増えることはありません**。`.new` が書き直されるのは、パッケージ更新でテンプレートが実際に変わり、`.new` の内容が古くなったときだけです（そのときは古い `.new` を退避してから上書きします）。

#### 2. `--diff`（変更の中身を端末で確認する）

**`--diff` を付けると、上書き更新・保護対象のファイルについて変更の中身（unified diff）を端末に表示します。** 「あなたの現在の版（`-`）→ 最新テンプレート（`+`）」の差分です。`.new` を書き出す前に、何が変わるのかをその場で把握できます。

```bash
# 変更の中身を見るだけ・何も書き込まない（最も安全）
npx @trimix/ai-team upgrade --dry --diff
```

`--dry --diff` の組み合わせは、**差分を確認するだけで書き込みもバックアップも一切行わない**、最も安全な使い方です。まずこれで変更内容を把握し、問題なければ `--diff` なしで適用する、という流れを推奨します。

> **`*.new` は `.gitignore` に追加しないでください（意図的な設計）。** `.new` は「あなたがまだ取り込んでいない未処理の作業」を表します。`.gitignore` に入れてしまうと `git status` に現れず、取り込み忘れ・削除忘れに気づけなくなります。`.new` があえてバージョン管理の視界に入ることで、「取り込んで消す」という対応を促します（バックアップ `.ai-team-backups/` が自動的に `.gitignore` へ追記されるのとは、狙いが逆である点に注意してください）。

## `.github/ISSUE_TEMPLATE/` は対象外

`upgrade` が更新するのは **`.claude/` 配下のみ**です。`.github/ISSUE_TEMPLATE/` に配置されるチケットテンプレートは `.claude/` の外にあるリポジトリ設定のため、`upgrade` の対象外です。

ただし黙って落とすのではなく、対象外であることを実行時に明示します。

```
  ℹ️  以下は .claude/ 外のリポジトリ設定のため upgrade の対象外です（更新するには /ai-team-setup で再配置してください）:
     - .github/ISSUE_TEMPLATE/（backend, frontend）
```

チケットテンプレートを最新化したい場合は、[/ai-team-setup](setup.html) を再実行して再配置してください。

## シンボリックリンク・ハードリンクは辿らずスキップします

`upgrade` は、**`.claude/` 配下のみを更新する**という約束を守るため、書き込み先へ至る経路にリンクがある場合は辿らずスキップします。ファイルのコピー（`copyFileSync`）とディレクトリ作成（`mkdirSync`）はいずれも経路上のリンクを辿るため、これを検査せずに書き込むと、`.claude/` の外にあるリンク先を意図せず書き換えてしまいます。

`.claude/` 丸ごと、あるいは `.claude/teams/` などをドットファイル管理リポジトリへシンボリックリンクする運用は珍しくありません。こうした場合、`.claude/teams/backend/workflow.yml` の**最終要素（葉）は実ファイルでも、途中のディレクトリ（`.claude` や `.claude/teams`）がリンク**になっていることがあります。

### 封じ込め検査（パス要素の走査）

書き込み先については、**プロジェクトルート（`cwd`）から書き込み先まで、パスの各要素を1つずつ降りながらシンボリックリンクかどうかを検査**します。葉だけでなく**中間ディレクトリのリンクも検出**し、1つでもリンクがあればその書き込みをスキップします。

- **存在しない要素はスキップ**します（これから作られるため）。
- **壊れたリンク**（リンク先が存在しないリンク）も、リンクであること自体は検出できるため正しく弾きます。
- **`.claude/` の内側で完結するリンク**（リンク先も `.claude/` 配下）も、内外を判別せず**一律でスキップ**します（安全側に倒す判断です）。
- 検査対象は**本体ファイルと、保護ファイルの隣に書き出す `<ファイル名>.new` の両方**です。

> **なぜ経路の走査なのか**: 「リンクを解決した実パスが `.claude/` の内側かどうか」で判定する方式（`realpath`）は、**壊れたリンクを誤って「内側」と判定**してしまいます（存在しないリンク先を安全とみなし、書き込みで実体化させてしまう）。そのため、実パス解決ではなく、経路の各要素を `lstat` で1つずつ検査する封じ込め方式を採っています。

### ハードリンクも検出します

書き込み先が**ハードリンク**（同じ実体＝inode を複数の名前が共有している状態）だった場合もスキップします。ハードリンクはシンボリックリンクとしては検出できませんが、`copyFileSync` / `writeFileSync` は共有 inode の中身をその場で書き換えるため、`.claude/` の外にある実体を破壊してしまいます。バックアップも同じ実体を指すため退避の意味を持ちません。そこで、書き込み前に `nlink`（実体を指す名前の数）が 1 を超えていないか検査します。

ハードリンク検査は、**本体ファイル（`dest`）・保護ファイルの隣に書き出す `<ファイル名>.new`・`.gitignore`（`.ai-team-backups/` の追記先）のすべて**で行います。シンボリックリンクの封じ込め検査と同じ範囲を、ハードリンクについても漏れなく適用します（`.new` がハードリンクのときは、完了報告で「ハードリンクのため書き出しをスキップしました」と種別に応じて案内します）。

### スキップの表示

スキップしたリンクは**黙って落とさず**、差分の提示と完了報告の両方で明示します。**シンボリックリンクとハードリンクの別、およびリンク先パス**を表示します。

```
  ⚠️  リンクのためスキップします（.claude/ の外を書き換えず、外部 inode も壊さないため）:
     - .claude/teams/backend/workflow.yml: シンボリックリンク → /path/to/dotfiles/workflow.yml
     - .claude/teams/backend/agents/tech-lead.md: 祖先 .claude/teams がシンボリックリンク → /path/to/dotfiles
     - .claude/model-profiles.yml: ハードリンク（外部 inode を共有・nlink=2）
   シンボリックリンクは解除するかリンク先を直接編集し、ハードリンクは通常ファイルに置き換えてください。
```

- スキップしたリンクは**バックアップにも退避しません**（触らないため退避も不要です）。
- 他のファイルの更新は**そのまま続行**します（リンク 1 つのために全体を中止することはありません）。
- `--force` を付けても、シンボリックリンク・ハードリンクのいずれも辿りません。上書き保護（`# customized: true`）とは別の、常時有効な安全策です。

リンク先のファイルもテンプレートへ更新したい場合は、シンボリックリンクなら解除して実ファイルに戻すか、リンク先を直接編集してください。ハードリンクなら実体をコピーした通常ファイルに置き換えてください。

### `.gitignore` と `.ai-team-backups` のリンク

`.claude/` 配下以外でも、`upgrade` が書き込む次の 2 箇所についてリンクを検査します。扱いはそれぞれ異なります。

| 書き込み先 | リンクだった場合の動作 |
|-----------|------------------------|
| `.gitignore`（`.ai-team-backups/` の追記先） | **シンボリックリンク・ハードリンクのいずれでも追記せず警告**します。リンク先／共有 inode（`.claude/` の外）を書き換えないためです。必要ならリンク先に手動で追記してください |
| `.ai-team-backups`（バックアップの退避先） | **シンボリックリンクなら、バックアップを中止し終了コード 1 で停止**します（fail-closed）。バックアップは最後の防衛線であり、退避先が信頼できない状態で適用に進んではならないためです |

`.ai-team-backups` がリンクのときの停止メッセージは次のとおりです。

```
❌ バックアップに失敗したため、アップグレードを中止します: バックアップ先 .ai-team-backups がシンボリックリンクです（→ /path/to/external）。信頼できない退避先へはバックアップできないため中止します（fail-closed）。
   （fail-closed: バックアップできない状態での上書きは行いません）
```

## 非対話環境での挙動

`upgrade` は破壊的な上書きを無確認で走らせないため、**確認応答を取得できない非対話環境（パイプ実行・CI など、標準入力が端末でない場合）では、`--yes` が無い限り安全側に倒して中止**します。

```
⚠️  非対話環境のため確認を取得できません。安全のためアップグレードを中止します。
   意図的に続行する場合は --yes を付けて再実行してください。
```

CI などから意図的に実行する場合は、`--yes` を明示的に付けてください。

## 更新の有無を通知する

`upgrade` の実行時（および `npm install` の `postinstall` 完了時）には、導入済みプラグインのバージョンと配布物側の最新バージョンを比較し、差があれば通知します。

```
🔔 更新があります: 導入済みプラグインより新しいバージョンが registry にあります
   - バックエンドチーム: v1.0.0 → v1.1.0
   最新テンプレートへ更新するには: npx @trimix/ai-team upgrade [team_id]
```

これは、導入先プロジェクトの `ai-team-plugins.json` に記録された「導入時のバージョン」と、配布物の `registry.json` に記載された「最新バージョン」を突き合わせた結果です。更新に気づけるようにするための通知であり、更新の実行自体は `upgrade` で行います。

## 使い方の流れ（推奨）

1. パッケージを更新する（`npm install --save-dev ./trimix-ai-team-x.x.x.tgz`）
2. まず `npx @trimix/ai-team upgrade --dry --diff` で、変更の中身まで確認する（何も書き込みません）
3. 問題なければ `npx @trimix/ai-team upgrade` を実行し、確認して適用する（適用直前にバックアップが作成されます）
4. 保護されたファイルは隣に `<ファイル名>.new` が書き出されます。差分を取り込み、済んだら `.new` を手動で削除する
5. カスタマイズ済みファイルを丸ごと最新へ揃えたい場合のみ、内容を確認したうえで `--force` を付けて再実行する
6. 不要になったバックアップ（`.ai-team-backups/`）は手動で削除する
