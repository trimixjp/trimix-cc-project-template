# バックエンドエージェント

バックエンドチームに含まれる 7 つのエージェントの詳細です。各エージェントの起動条件・動作フロー・出力するコメントフォーマットを定義しています。

> **定義場所**: `.claude/teams/backend/agents/*.md`

---

## エージェント一覧

| エージェント | ファイル | 役割 |
|------------|---------|------|
| Tech-Lead | `tech-lead.md` | リーダー。要件分析・設計方針決定・レビュー方式判断 |
| Implementer | `implementer.md` | 実装担当 |
| Reviewer | `reviewer.md` | シングルレビュー担当 |
| Reviewer-A | `reviewer-a.md` | ダブルレビュー A 担当・クロスレビューのリード |
| Reviewer-B | `reviewer-b.md` | ダブルレビュー B 担当 |
| Tech-Writer | `tech-writer.md` | ドキュメント更新担当（[専用ページ](tech-writer.html)） |
| PR-Creator | `pr-creator.md` | PR 作成担当 |

---

## Tech-Lead

バックエンドチームのリーダーです。

### 起動条件

1. `backend:tech-lead` ラベル付与
2. Dispatcher から直接ディスパッチ
3. Reviewer からの差し戻しで再設計が必要と判断

### 動作フロー

1. **インシデント確認**: `.claude/incidents/index.yml` を読み込み、関連インシデントがあれば Issue 本文末に注意事項を追記
2. **要件分析・設計方針決定**: 機能要件・非機能要件・影響範囲・技術的制約・リスクを分析
3. **Implementer への振り分け**: 設計方針をコメント記録 → `backend:implementer` ラベル付与
4. **レビュー方式判断**（Implementer 完了後）: `review-config.yml` を参照してシングル / ダブルを判定

### コメントフォーマット（設計方針）

```
🔧 Tech-Lead: 設計方針を決定しました

## 要件分析
- 機能要件: ...
- 非機能要件: ...
- 影響範囲: ...

## 設計方針
（実装アプローチ・アーキテクチャ上の判断）

## 参照仕様書・ドキュメント
- `docs/xxx.md`（参照箇所: セクション名）

## 判断根拠
（代替案と選択理由を含む）

## 懸念点・注意事項
- （未解決の懸念点があれば「未解決」と明記。なければ「なし」）

## Implementer への指示
- （実装タスクを箇条書きで）

⏭️ 次のアクション: backend:implementer に引き継ぎます
```

### コメントフォーマット（レビュー方式判断）

```
🔧 Tech-Lead: レビュー方式を判断しました

## 影響範囲の分析
- 変更ファイル数: <件数>
- 変更対象領域: <認証 / DB / API / Frontend 等>
- 複数レイヤーの変更: あり / なし
- 付与ラベル: <ラベル名>

## 判断結果: シングルレビュー / ダブルレビュー

判断理由:
- （該当した基準を列挙）

⏭️ 次のアクション: <backend:reviewer / backend:reviewer-a + backend:reviewer-b> に引き継ぎます
```

### 重要な原則

- Tech-Lead 自身はコードを書かない（必ず Implementer に委譲）
- 全ての設計判断には参照仕様書を明記
- 懸念点は「未解決」として明示・隠蔽禁止
- インシデント確認は作業開始前に必ず実施

## Implementer

実装担当エージェントです。

### 起動条件

1. `backend:implementer` ラベル付与
2. Reviewer からの差し戻しで `backend:implementer` ラベル再付与

### 動作フロー

1. **設計方針の確認**: Tech-Lead のコメントから機能要件・実装アプローチ・指示を把握
2. **実装**: 設計方針に従いコード実装（逸脱前は Tech-Lead に確認）
3. **テスト実行・確認**: 既存テスト通過・新規テスト追加・リント
4. **完了報告コメント投稿**

### コメントフォーマット

```
🛠️ Implementer: 実装が完了しました

## 変更ファイル一覧
| ファイルパス | 変更内容の概要 |
|-------------|---------------|
| `src/xxx.ts` | ... |
| `tests/xxx.test.ts` | ... |

## 実装内容
（Tech-Lead の設計方針に対して、何をどのように実装したか）

## 設計方針からの変更点
- （あれば理由とともに記述。なければ「なし」）

## テスト結果
- 既存テスト: 全件パス
- 新規テスト: 全件パス / 追加件数: <件数>
- リント: エラーなし

## 懸念点・注意事項
- （「未解決」と明記）

⏭️ 次のアクション: Tech-Lead へ完了を通知します
```

### 実装時の遵守事項

- 設計方針から逸脱する場合は事前に Tech-Lead に確認
- セキュリティ・法的判断が必要な箇所では即座にエスカレーション
- ハードコードされたシークレットを含めない
- 新規実装箇所にはテストを追加

## Reviewer（シングルレビュー）

シングルレビュー担当です。

### 起動条件

1. `backend:reviewer` ラベル付与
2. Implementer の完了報告コメントが投稿済み

### レビュー観点

| 観点 | 判定基準 |
|------|---------|
| 可読性 | 変数名・関数名が意図を明確に表現 |
| 関数の責務 | 1 関数が単一責務、50 行以内が目安 |
| 重複排除 | 同一ロジックが複数箇所に存在しない |
| エラーハンドリング | 失敗しうる処理に適切な処理 |
| セキュリティ | ハードコードされたシークレットなし・外部入力検証 |
| 設計との整合 | Tech-Lead の方針に従って実装 |
| テスト | 新規実装箇所のテスト・正常系・異常系カバー |

### 合否判定

- **合格**: `contributor:ready` ラベル付与 → Contributor へ
- **不合格**: `backend:implementer` ラベルに戻して差し戻し（同一指摘 3 回以上は Tech-Lead に設計見直しを依頼）

### コメントフォーマット（差し戻し）

```
❌ Reviewer: 差し戻し

## 指摘事項

### CRITICAL（必ず修正）
- [ ] （指摘内容。該当ファイルと行番号を明記）
  - 問題: ...
  - 根拠: ...
  - 修正方針: ...

### HIGH（原則修正）
- [ ] ...

### MEDIUM（改善推奨）
- [ ] ...

## 参照した根拠
- （根拠として参照したファイルパス）

⏭️ 次のアクション: backend:implementer に差し戻します
```

CRITICAL 指摘が 1 件でもある場合は必ず不合格とします。

## Reviewer-A / Reviewer-B（ダブルレビュー）

ダブルレビューは「独立レビュー → クロスレビュー」の 2 段階で行われます。Reviewer-A がクロスレビューをリードし、Reviewer-B が応答します。

### 起動条件（共通）

1. `backend:reviewer-a` または `backend:reviewer-b` ラベル付与
2. Implementer の完了報告コメントが投稿済み
3. `review-config.yml` で `mode` が `double` 相当（または Tech-Lead がダブル判定）

### 動作フロー

**段階 1: 独立レビュー**

- お互いのコメントを読まずに、Tech-Lead の方針と Implementer の実装をレビュー
- 暫定判定コメントを投稿（最終判定はまだ確定しない）

**段階 2: クロスレビュー**

- 両者の独立レビュー完了後、Reviewer-A がリードして比較・議論
- Reviewer-B が応答（Reviewer-A の指摘への賛否・独自の指摘）
- Reviewer-A が最終判定コメントを投稿

### Reviewer-A の独立レビューコメント

```
🔍 Reviewer-A: 独立レビュー完了（暫定）

※ このレビューはReviewer-Bの結果を見ずに独立して行いました

## レビュー結果（暫定）

| 観点 | 結果 |
|------|------|
| コード品質 | 合格 / 要修正 |
| 設計との整合 | 合格 / 要修正 |
| テスト | 合格 / 要修正 |

## 指摘事項（あれば）
- （指摘内容と根拠）

Reviewer-B の独立レビュー完了後にクロスレビューを実施します。
```

### Reviewer-A のクロスレビューコメント（最終判定）

```
🔀 Reviewer-A: クロスレビュー完了 → 最終判定

## Reviewer-B との差異確認

| 指摘項目 | Reviewer-A | Reviewer-B | 最終判断 |
|---------|-----------|-----------|---------|
| <項目> | 合格/指摘 | 合格/指摘 | <結論> |

## 差異があった場合の議論結果
（議論の経緯と結論）

## 最終判定: 合格 / 不合格

⏭️ 次のアクション: <backend:tech-writer に引き継ぎ / backend:implementer に差し戻し>
```

### Reviewer-B のクロスレビュー応答コメント

```
💬 Reviewer-B: クロスレビューへの応答

## Reviewer-A の指摘への見解

| Reviewer-A の指摘 | Reviewer-B の見解 | 合意 |
|-----------------|-----------------|------|
| <指摘内容> | <賛成/反対+理由> | 合意/不合意 |

## Reviewer-B 独自の指摘（Reviewer-A が見逃していた点）
- （あれば記述。なければ「なし」）
```

### 重要な原則（共通）

- 独立レビュー中は相手のコメントを読まない
- 全ての指摘には根拠（ルール・仕様書）を明記
- クロスレビューで差異があった場合は議論の経緯を必ず記録
- 意見が一致しない場合は Human-Escalator を呼び出し

## PR-Creator

プルリクエスト作成担当です。

### 起動条件

1. `backend:pr-creator` ラベル付与
2. Reviewer の合格コメント後、Tech-Lead がラベルを更新

### 動作フロー

1. **情報収集**: Issue 全コメントから設計方針・実装内容・テスト結果・レビュー結果を収集
2. **PR 作成**: `gh pr create` を実行
3. **承認依頼**: Issue に承認依頼コメント投稿 + `escalated:human` ラベル付与

### PR 作成コマンド

```bash
gh pr create \
  --title "<タイトル>" \
  --body "<本文>" \
  --base main \
  --head <feature-branch>
```

### PR 本文フォーマット

```markdown
## 概要
<この PR が解決する問題・追加する機能を2〜3行>

## 関連 Issue
Closes #<Issue番号>

## 変更内容
<Implementer の完了報告から転記>

| ファイルパス | 変更内容の概要 |
|-------------|---------------|
| `src/xxx.ts` | ... |

## 設計方針
- 採用したアプローチ: ...
- 選択の根拠: ...

## テスト
- 既存テスト: 全件パス
- 新規テスト: <件数>件追加・全件パス
- リント: エラーなし

## レビュー結果
<Reviewer の合格コメントから要約>

## チェックリスト
- [ ] CI がパスしている
- [ ] セルフレビュー完了
- [ ] レビュアーの承認済み（エージェントレビュー）
```

### Issue 承認依頼コメント

```
🔀 PR-Creator: プルリクエストを作成しました

PR: <PR URL>
タイトル: <PR タイトル>
マージ先: main

---
⚠️ 承認・マージは人間が行います

確認ポイント:
- 設計方針が意図通りか
- テストが十分か
- 変更範囲が適切か

⏸️ 人間の承認があるまで処理を停止します
```

### 重要な原則

- PR の承認・マージは常に人間が行う
- マージ後の Issue クローズは行わない（Contributor が担当）
- ブランチ不在・コンフリクトは Tech-Lead に報告

---

## エスカレーション条件（共通）

各エージェントは以下に該当した場合 `human-escalator` を呼び出します。

- セキュリティ脆弱性発見（`legal`）
- 法的判断が必要な実装（`legal`）
- PR の承認・マージが必要（`merge_approval`）
- 設計方針が決定不能（`ambiguous_spec`）
- 費用が発生するサービス利用が必要（`budget`）
- `.claude/escalation-rules.yml` の `escalation_triggers` に該当

詳細は [エスカレーションルール](../reference/escalation.html) を参照してください。

---

## 共通エージェントへのリンク

- `contributor` / `dispatcher` / `human-escalator` は `.claude/agents/` 配下に配置され、全チーム共通で動作します
- これら共通エージェントの詳細仕様は本リファレンスの [エスカレーションルール](../reference/escalation.html) と各チームページの「ワークフロー全体フロー」を参照してください
