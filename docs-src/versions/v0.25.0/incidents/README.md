# インシデント管理ガイド

このディレクトリは AIチームが学習・参照するインシデント記録を管理します。

---

## ディレクトリ構成

```
incidents/
├── index.yml          # インシデントインデックス（一次記録者が追記。Contributorが整合性を検証）
├── TEMPLATE.md        # インシデントファイルのテンプレート
├── README.md          # このファイル
└── YYYYMMDD-*.md      # 個別インシデントファイル（一次記録者が生成。Contributorが拾い上げ・検証）
```

---

## インシデントが記録される条件

以下のいずれかに該当する場合、インシデントファイルが記録されます。記録は**失敗が発生したその時点**（差し戻し・エスカレーション・作業中の事故の発生時）で一次記録者が行い、Contributor はチケットクローズ時に記録の拾い上げと検証を行います（詳細は次節「責務分担」）。

| 条件 | 例 |
|------|-----|
| 本番障害が発生した | APIが応答不能、データ損失 |
| セキュリティインシデントが発生した | 不正アクセス、権限設定ミス |
| 重大なバグが本番環境に影響した | P1/P2の本番バグ |
| 設定ミス・操作ミスで障害が発生した | Terraform誤操作、DNS設定ミス |
| 差し戻し（レビュー不合格）が発生した | 同一クラスの欠陥での再修正 |
| `escalated:human` への遷移が発生した | AIだけでは解決できない判断 |
| 再発防止のために記録すべき教訓がある | 類似ミスの防止 |

上記に該当しない場合は「✅ Contributor確認済み — インシデント対象外」とコメントしてチケットをクローズします。

## 責務分担（Issue #89 以降の記録モデル）

インシデントの**一次記録責任**は、失敗が顕在化した時点でその遷移を実際に扱うエージェントが負います。Contributor の役割は「ゼロからの記録」ではなく、**①記録し漏らした事象の拾い上げ**と**②既に記録された事象の内容・`index.yml` 登録の検証**に縮退しています（Contributor の役割縮退は「レビューを省く」という意味ではなく、あくまで「インシデント記録の一次責務の移管」です）。

| 記録主体 | 記録タイミング | 担当範囲 | 定義箇所 |
|---------|---------------|---------|----------|
| オーケストレーター（`/ai-team-run`） | 差し戻し・エスカレーション・再実装起動前の3発火点（次節） | 全チーム共通（workflow.yml の遷移を実際に処理するため） | `skills/ai-team-run.md`「インシデントの即時記録と再照合」 |
| 各チームリーダー（例: Tech-Lead） | 自身が差し戻しを発する場合の補助記録 | 自チームの差し戻し・エスカレーション・作業事故 | 各チームリーダー定義（例: `tech-lead.md`）「失敗の即時記録」節 |
| Human-Escalator | `escalated:human` への遷移時 | 全チーム共通のエスカレーション実務 | `human-escalator.md`「ステップ3.5: インシデント記録」 |
| Contributor | チケットクローズ時 | 記録漏れの拾い上げ・既存記録の検証 | `contributor.md`「ステップ5: インシデント調査」 |

**dedup（重複記録の回避）**: 記録前に必ず `index.yml` を読み、当該チケット番号（`issue`）と事象に対応するエントリが既にあるか照合します。既に記録済みなら新規レポートを作らず、既存エントリの不足（`keywords`・再発防止策等）を補うのみとします。この方針は上記すべての記録主体に共通です。

## 3つの発火点（オーケストレーターの責務）

`/ai-team-run` は以下の3つの発火点で記録・再照合を行います（詳細: `skills/ai-team-run.md`「インシデントの即時記録と再照合」）。

1. **発火点1: 差し戻しコメント投稿の直前（`on_rework`）** — 差し戻しの原因・争点をその場で記録します。Contributor のクローズ処理を待ちません。
2. **発火点2: `on_rework.next` の再実装担当を起動する前** — `index.yml` を照合し、関連する再発防止策を再実装担当への作業指示に明記して反映してから起動します。差し戻しのたびに実施します。
3. **発火点3: `escalated:human` への遷移時（`on_escalation` / `rework_limit` 超過）** — その原因と経緯を記録します。Human-Escalator と dedup で重複を避けます。

> **位置づけの注意**: 記録・再照合は**補助**であり、差し戻しループを防ぐ主軸は**対象の事前全列挙**（境界・横断的関心事の全経路を修正着手時に先に確定させること）です。過去の教訓は失敗の変種しか含まないため、記録・再照合だけに頼ると同じ「単数形で狭く書く癖」を繰り返します（`tech-lead.md`「失敗の即時記録と網羅的な仕様化」節を参照）。

## インシデントファイルの作成（一次記録者・Contributor 共通）

```
ファイル名: YYYYMMDD-<概要をkebab-case>.md
内容: TEMPLATE.md に従って記載
  - ⛔ やってはいけないこと
  - ⚠️ 注意事項
  - 根本原因
  - タイムライン
  - 再発防止策
```

## index.yml への追記

```yaml
- id: <次の連番>
  date: "YYYY-MM-DD"
  file: "incidents/YYYYMMDD-*.md"
  title: "インシデントの概要タイトル"
  severity: P1 / P2 / P3
  teams: [backend, infra, content]
  issue: <チケット番号>
  keywords: [関連キーワードのリスト]
```

## エージェントによる活用方法

### Tech-Lead / Infra-Lead / Editor-in-Chief（作業開始時）

```
1. index.yml を読み込む
2. チケットのタイトル・ラベル・内容とkeywordsを照合する
3. 関連インシデントが見つかった場合はチケット本文末に注意事項を追記する
```

### オーケストレーター（差し戻し・エスカレーション・再実装起動前）

```
1. 差し戻しコメント投稿の直前に記録する（発火点1）
2. 再実装担当を起動する前に index.yml を照合し、再発防止策を作業指示へ注入する（発火点2）
3. escalated:human へ遷移する時点で記録する（発火点3）
```

### Human-Escalator（escalated:human への遷移時）

```
1. index.yml を照合し、オーケストレーターが記録済みでないか確認する（dedup）
2. 未記録の場合はインシデントファイルを作成しindex.ymlを更新する
3. 記録した参照パスをエスカレーションコメントに併記する
```

### Contributor（クローズ時: 拾い上げ・検証）

```
1. クローズするチケットの内容を分析する
2. 機械的基準（差し戻し2回以上・真のエスカレーション・DOD未達 等）でインシデント記録の要否を判定する
3a. 既に記録済み → 内容とindex.yml登録を検証し、不足を補う
3b. 未記録（記録漏れ） → 拾い上げとして新規に記録する
```
