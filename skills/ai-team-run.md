# /ai-team-run — ワークフロー起動

あなたはAIチームのオーケストレーターです。担当チケットを読み込み、適切なワークフローを起動してください。

## チケット操作（必須）

チケットの作成・一覧・詳細・コメント・ラベル・クローズは **`/ai-team-ticket`** スキル経由で行います（内部で共通 CLI を実行。github / local 両対応）。

| 操作 | スキル呼び出し例 |
|------|------------------|
| 作成 | `/ai-team-ticket create --title "題名" --body "本文" --label backend:tech-lead` |
| 一覧 | `/ai-team-ticket list` |
| 詳細 | `/ai-team-ticket view 1` |
| コメント | `/ai-team-ticket comment 1 --body "メモ"` |
| ラベル | `/ai-team-ticket edit 1 --add-label L1 --remove-label L2` |
| クローズ | `/ai-team-ticket close 1` |
| 設定確認 | `/ai-team-ticket backend` |

エージェント自身がツールで実行する場合も、同等の CLI（`npx @trimix/ai-team ticket ...`）を使ってください。`gh issue` の直叩きは禁止です（github 時は CLI が内部で `gh` を呼びます）。
`ticket_backend: local` のときチケットは `tickets/open/*.md`（設定の `local_tickets.dir`）に置かれます。人間向け UI は **Obsidian で `tickets/` を vault として開く**運用を推奨（エージェントはファイルのみ参照）。詳細は `.claude/docs/local-tickets.md`。

## 引数

```
/ai-team-run <チケットURL または チケットID または 問題の説明>
```

引数が省略された場合は、ユーザーにチケットのURLまたは内容の貼り付けを求めてください。

## 書き込みの同意（最初の書き込みの前に1回）

チケットの作成・コメント・ラベル変更と、feature ブランチの push・PR の作成は、外部への公開に当たります（`ticket_backend: local` でも push と PR は外に出ます）。`/ai-team-run` の起動は作業の指示であって、書き込みの同意ではありません。**最初の書き込みの前に1回だけ**、範囲を具体的に1文で確かめてください（決定: 2026-11-22、Issue #125。理由: 外部への公開は、範囲を明示して同意を取ってから行う。作業の指示を書き込みの同意と読み替えない）。

聞き方（はい／いいえで答えられる1文）:

```
#42 のワークフローが人の判断待ち（PR の承認待ち、または escalated:human）に戻るまで、#42 へのコメント・ラベル変更と、feature ブランチの push・PR 作成を行ってよいですか
```

- **聞く時点**: パターンA（番号・URL）はチケットを読んだ直後で、ステップ4の注意事項コメントより前。パターンB（自由記述）はチケットを作る前で、作成の案と範囲を1文にまとめて聞く（ステップ1 B-2）。Epic（Dispatcher）では、サブチケットの作成も範囲に含めて聞く
- **返事を待つ間**: 書き込みの要らない作業を進める（チケットの読み込み、チームとワークフローの特定、`.claude/incidents/index.yml` の照合、エージェント定義の読み込み）
- **同意の範囲**: 1文で示した範囲だけです。ワークフローが人の判断待ち（`escalated:human` の付与、PR の承認待ち）に戻った時点で終わります。`/ai-team-resume` で再開するときは、改めて同じ形で確かめます。人が範囲を明示して完了まで任せた場合（マージの代行を含む。`.claude/escalation-rules.yml` の `merge_approval`）は、書き込みの同意の範囲もその完了（マージ後のコメント・ラベル変更・クローズ）まで広がります
- **聞かなくてよい場合**: 起動の指示そのものに範囲が書かれている場合（例: 「#42 を PR 作成まで進めて。コメントと push も任せる」）と、直前に同じ範囲の同意を得ている場合（例: プロジェクトの CLAUDE.md の「タスク受付ルール」で、チケットの作成と一緒に確かめた）は、その範囲を1行で表示して進めます。`/ai-team-watch`（ソロモード）は、setup で `mode: solo` を選んだ時点の同意で代え、聞きません
- **同意が得られない場合**: 書き込まずに、ここまでに分かったこと（担当チーム・関連インシデント・次に行う予定だった書き込み）をターミナルに示して停止します
- 同意はターミナルのやり取りで完結させ、チケットにはコメントしません（範囲は人の判断待ちで終わり、再開のたびに確かめ直すため）

## ステップ1: 引数の種別を判定して読み込む

引数の形式によって処理を分岐してください。

### パターンA: チケット番号（数字のみ）または GitHub URL

```bash
npx @trimix/ai-team ticket view <番号>
```

URLのパターンから自動判別：
- `github.com/.*/issues/*` → 番号を抽出して `ticket view`（`ticket_backend: github` 前提）
- `local://tickets/<id>` → 番号を抽出して `ticket view`（local）
- `*.atlassian.net/browse/*` → Jira（URLの内容をユーザーに貼り付けてもらう）

チケットが取得できたら**ステップ2へ進む**。

### パターンB: 自由記述テキスト（問題・依頼の説明文）

番号でも URL でもない文字列が渡された場合（例: `/ai-team-run ログインAPIがエラーを返す`）は、以下の手順で **チケットを起点にしてからワークフローを起動**してください。

> **なぜチケット経由が必須か**: インシデント記録・ラベルによる状態管理・作業履歴の追跡はチケットベースで動作します。

#### B-1: 既存チケットの検索

入力テキストからキーワードを抽出して、関連する open チケットを検索してください：

```bash
# local / github 共通（キーワード絞り込みは list 結果を JSON で読んでフィルタ）
npx @trimix/ai-team ticket list --state open
```

**候補が見つかった場合:**

一覧を示し、最も近い候補とその理由を添えて、はい／いいえで答えられる1文で確かめてください：

```
以下の既存チケットが見つかりました：
- #12: [タイトル] ([ラベル])
- #15: [タイトル] ([ラベル])

#12（題名の「ログインAPI」に一致）を使ってよいですか。違えば新しく作ります
```

- 既存チケットを使う → そのチケット番号でステップ2へ
- 新規作成 → B-2へ

**候補が見つからなかった場合:** B-2へ

#### B-2: 新規チケットの作成

入力テキストから以下を判断して チケットを作成してください：

1. **タイトル**: 入力内容を要約した短いタイトル（50文字以内）
2. **本文**: 入力テキストをそのまま含め、背景・現象・対応方針を構造化
3. **ラベル**: 下表のキーワード対応でチームラベルを推定する（上から順に評価し、最初に一致した行を採用。導入していないチームの行は読み飛ばす）

| タイトル・本文のキーワード（いずれかを含む） | 付与するラベル |
|---|---|
| 複数チームにまたがる・横断・全体 | `epic` |
| 障害・本番エラー・緊急 | `incident` |
| API・DB・サーバ・バッチ・認証・バックエンド | `backend:tech-lead` |
| 画面・UI・コンポーネント・CSS・フロントエンド | `frontend:designer` |
| インフラ・クラウド・ネットワーク・デプロイ・セキュリティ | `infra:infra-lead` |
| 記事・ドキュメント・README・文章 | `content:editor-in-chief` |
| SNS・X・Instagram・投稿文 | `sns:strategist` |
| YouTube・動画・台本・チャンネル | `youtube:director` |
| どの行にも一致しない | ラベルなしで作成し、ステップ3の「ラベルがない場合」で確認する |

作成の前に、タイトル・本文・ラベルの案を示し、作成とその後の書き込みの範囲を1文で確かめてください（「書き込みの同意」の節）。例: 「この案で `backend:tech-lead` のチケットを作成し、そのワークフローが人の判断待ちに戻るまで、コメント・ラベル変更と feature ブランチの push・PR 作成を行ってよいですか」。同意が得られなければ作成しません。

```bash
npx @trimix/ai-team ticket create \
  --title "<タイトル>" \
  --body "<本文>" \
  --label "<推定ラベル>"
```

作成した チケットの番号を取得し、ステップ2へ進んでください。

### パターンC: 引数なし

ユーザーにチケットの URL・番号・または問題の説明の入力を求めてください。入力されたらパターンA/Bで処理します。

## ステップ2: 前提確認

`.claude/` ディレクトリが存在しない場合は、セットアップが完了していないことをユーザーに伝え、`/ai-team-setup` を先に実行するよう案内してください。

## ステップ3: チームとワークフローの特定

チケットの**ラベル**・**タイトル**・**内容**から、担当チームとワークフローを判断してください。

### ラベルによる判断（優先）

| ラベルのプレフィックス | 担当チーム | ワークフロー |
|----------------------|-----------|------------|
| `backend:*` | バックエンドチーム | `.claude/teams/backend/workflow.yml` |
| `frontend:*` | フロントエンドチーム | `.claude/teams/frontend/workflow.yml` |
| `content:*` | コンテンツチーム | `.claude/teams/content/workflow.yml` |
| `infra:*` | インフラチーム | `.claude/teams/infra/workflow.yml` |
| `sns:*` | SNSチーム | `.claude/teams/sns/workflow.yml` |
| `youtube:*` | YouTube動画制作チーム | `.claude/teams/youtube/workflow.yml` |
| `epic` または `dispatcher` | Dispatcher | 各チームに分解 |
| `incident` | インシデント対応 | 緊急対応フロー |
| `escalated:human` | 人間対応待ち | ワークフロー停止中（解除後は /ai-team-resume で再開） |

### 複数チームのラベルが併存する場合（タイブレーク）

チームプレフィックス（`backend:` 等）のラベルが複数チーム分付いている場合は、以下で判定します。

1. ラベル付与イベントを時系列で取得し、**最も後に付与されたチームラベル**のチームを採用する

```bash
gh api "repos/<owner>/<repo>/issues/<番号>/events" --paginate \
  --jq '.[] | select(.event=="labeled") | .label.name'
```

2. コマンドが失敗した場合、または付与順を判別できない場合は、候補チームを列挙し、推奨と理由を添えた1文で確かめる（例: 「#42 を backend チームで進めてよいですか（題名の『API』に一致し、`backend:tech-lead` が後から付いたとみられるため）」）

### ラベルがない場合

ステップ1 B-2 のキーワード対応表でチームを推定し、推定したチームと一致したキーワードを添えて、はい／いいえで答えられる1文で確かめてから起動してください（例: 「#42 を backend チームで始めてよいですか（本文の『API』『DB』に一致）」）。キーワード対応表には誤判定があるため、確認は省きません。

## ステップ4: インシデント確認

担当チームのワークフロー起動前に、`.claude/incidents/index.yml` を読み込み、チケット内容と `keywords` を照合してください。

**関連インシデントが見つかった場合:**
- 該当インシデントファイルを読み込む
- チケットにコメントとして注意事項を投稿する（`npx @trimix/ai-team ticket comment`。「書き込みの同意」を得てから）
- 注意事項コメントも、後述「コメントの表示構成（折りたたみ）」の構成で投稿する（1行目 `## ⚠️ 関連インシデント注意事項` → 人の判断が要る点の要点 → 各インシデントの詳細を `<details>` に入れる）

## ステップ5: ワークフローの起動

新規か再開かは、ラベルではなく、ステップの完了コメント（`⏭️ 次のアクション:` 行を含むコメント）の有無で判定します。

- **`⏭️ 次のアクション:` 行を含むコメントが1件も無い** → 新規です。特定したワークフローの最初のステップを実行します
- **1件以上ある** → 次の「途中から再開する場合」に従います

ラベルで判定しないのは、ステップ1 B-2 で作ったチケットや、Issue テンプレートから作ったチケットには、作った時点で先頭ステップのラベル（例: `backend:tech-lead`）が付いているためです。すべてのステップの完了コメントには `⏭️ 次のアクション:` 行があるので（「状態記録要件」）、この行の有無で、どれかのステップが終わっているかが分かります。

### 途中から再開する場合（ステップの完了コメントがある）

ステップの完了コメントがあるチケットは、最初のステップから始め直さず、続きのステップから始めます（セッションが途中で切れた場合や、`/ai-team-watch` が再開対象を処理する場合）。始め直すと、終わったステップの作業とコメントを重ねてしまうためです。

復帰先は次の表で決めます。`/ai-team-resume` の決定表（同スキルのステップ4。`エスカレーション元ステップ` の無い旧形式のエスカレーションコメント用）をもとにしていますが、適用する場面と行1の扱いが違うため、ここに別に置きます。

| # | 条件 | 復帰先 |
|---|------|--------|
| 1 | チームのステップのラベルがちょうど1つ付いている | そのラベルのステップ。同じラベルのステップが複数ある場合（例: backend の `backend:tech-lead` は `tech-lead-analysis` と `tech-lead-review-decision`）は、最後の `⏭️ 次のアクション:` 行で決める（resume の表には、この例外はありません） |
| 2 | 上記以外で、最後の `⏭️ 次のアクション:` 行からステップを読み取れる | **最後の** `⏭️ 次のアクション:` 行に書かれたステップ |
| 3 | どちらでも決まらない | 候補のステップと理由を添え、ユーザーに1文で確かめる |

始める前に、終わった作業を確かめます。

- 最後の `⏭️ 次のアクション:` 行と、復帰先のステップの完了コメントがすでにあるか
- 作業ブランチがあれば、`git log --oneline <base_branch>..HEAD`（`<base_branch>` は `review-config.yml` の値。worktree 方式なら `<workspace.worktree_dir>/issue-<番号>`〔既定 `.claude/worktrees/issue-<番号>`〕の中で実行）

進捗の記録は、今までどおりチケットのコメントと git のコミットです。進捗ファイルは作りません（チケットコメントが唯一の正で、二重に持つと食い違うため）。

### Epic / Dispatcher の場合

`.claude/agents/dispatcher.md` を読み込み、Dispatcher エージェントとして動作してください：
- チケット内容を分析してサブチケット（またはサブタスク）に分解
- 各チームのワークフローを並列または順次で起動

### 通常チケットの場合

ワークフロー定義（`workflow.yml`）の最初のステップのエージェント定義を読み込み、そのエージェントとして動作してください。

例（バックエンドチーム）:
```
workflow.yml の steps[0] = tech-lead-analysis
→ .claude/teams/backend/agents/tech-lead.md を読み込む
→ Tech-Lead として動作開始
```

### インシデントの場合

担当チームが不明な場合は、候補のチームと理由を添えた1文で担当チームを確かめ、あわせて `escalated:human` ラベルの付与を提案してください（例: 「#42 は障害の報告で担当チームを決めきれません。backend（本文の『API』に一致）で進めてよいですか。決められなければ `escalated:human` を付けて人の判断を待ちます」）。

## ステップ6: エージェントとしての動作

読み込んだエージェント定義に従い、チケットを処理してください。

### 委託するかどうか（判断基準）

ステップは、原則としてこのセッションで「そのエージェントとして」動きます。サブエージェント（Task/Agent ツール）へ委託するのは、次の4つのどれかに当たるときだけです（決定: 2026-11-22、Issue #125）。

| # | 委託する場面 | 例 |
|---|---|---|
| 1 | 並列のステップ（`next` が配列） | `reviewer-a` と `reviewer-b` |
| 2 | 大量のファイルを読んで、結論だけを受け取りたい調査 | 影響範囲の洗い出し。広い探索は Explore に任せる |
| 3 | エージェント定義の `model` が、このセッションのモデルと違うステップ | balance で、opus のこのセッションから `model: sonnet` の implementer を動かす |
| 4 | 独立した目で見る検証役（`model_role: verifier`） | reviewer・security-engineer・各 `*-qa` |

数回のツール呼び出しで済む確認や、場所が分かっている読み込みは委託せず、このセッションで行います。Dispatcher によるサブチケットの分解は、このセッションで Dispatcher として行います。Epic が大きく大量の読み込みが要る調査は 2 に、分解したサブチケットのワークフローを並列で動かすときは 1 に当たります。

**理由**: 委託すると、渡す文脈と受け取る報告の両方で情報が落ち、費用もかかるため、必要な場面に絞ります。ただし 1・2 だけに絞ると、エージェント定義の `model`（役割別モデル）がほとんど効きません。Claude Code では `.claude/teams/<team>/agents/` の定義はサブエージェントとして登録されず（登録されるのは `.claude/agents/` の共通エージェントだけ）、このセッションで「そのエージェントとして動作」すると、このセッションのモデルで動くためです。そこで 3・4 を加えます。3 は Claude Code の runtime を前提にしています（Grok Build ではエージェントを `.grok/agents/` にミラーします）。

**委託する場合は、後述「委託監視プロトコル（点呼・ウォッチドッグ）」の手順を必ず実施してください。** 報告の契約はこのスキルにだけ置き、エージェント定義へは複製しません。

**チケットへの記録:**  
各エージェントの作業結果はチケットのコメントとして記録します：
- `npx @trimix/ai-team ticket comment <番号> --body "..."` を実行（github/local 両対応）

**ラベルの更新:**  
次のエージェントへの引き継ぎ時はラベルを更新します：
- `npx @trimix/ai-team ticket edit <番号> --add-label "..." --remove-label "..."`（github/local 両対応）

**ワークフローの継続:**  
現在のエージェントの処理が完了したら、`workflow.yml` の `on_complete` に従い次のステップへ進んでください。人間のアクションが必要な場合（`escalated:human`、PR承認等）はそこで停止し、ユーザーに案内してください。

**ターミナルへの報告:**  
チケットのコメントとは別に、ターミナルで人に状況を伝えます。チケットのコメントの形（1行目・`⏭️ 次のアクション:` 行など）は変えません。チケットのコメントは記録で、ターミナルの人は途中を見ていないことがあるためです。

- ステップを始めるときと終えたときに、1行で伝える（例: `#42 implementer を開始` / `#42 implementer 完了: 変更 3 ファイル、npm test 120/120`）。数値は実測したものだけを書く
- 委託したステップは、委託先の報告（着手・主要ステップの完了・失敗）を受け取るたびに1行で中継する（サブエージェントの中の様子は人から見えないため）
- 停止するとき（承認待ち・エスカレーション・完了・書き込みの同意が得られない）は、わかった事・やった事・次の事を短くまとめ、人の対応が要るなら何をしてほしいかを1文で書く。途中を見ていない人が読んでも分かるように書く

**差し戻し・エスカレーション・再実装の遷移時:**  
`on_rework`（差し戻し）・`on_escalation`（エスカレーション）の遷移を行うとき、および `on_rework.next` の再実装担当を起動するときは、後述「インシデントの即時記録と再照合（発火点: 差し戻し・エスカレーション・再実装）」の3発火点を必ず実施してください（記録は失敗した時点で、再照合は再実装の担当を起動する前に行います）。

**並列起動（`next` が配列の場合）:**  
`on_complete.next` または `conditions[].next` が配列（例: `[reviewer-a, reviewer-b]`）の場合、列挙されたすべてのステップのラベルを一度に付与して並列起動します。

```bash
npx @trimix/ai-team ticket edit <番号> \
  --add-label "backend:reviewer-a" \
  --add-label "backend:reviewer-b" \
  --remove-label "<現在のラベル>"
```

**AND完了待機（次のステップに `requires_all_of` がある場合）:**  
完了後の次のステップに `requires_all_of: [A, B, ...]` が設定されている場合は、以下の疑似コードのとおりに遷移してください。ラベルは**毎回 `npx @trimix/ai-team ticket view <番号>` で最新を再取得**し、以前に取得した結果を使い回してはいけません（並列ステップの完了はラベル除去で表現されるため、ラベルの有無が完了状態の指標です）。

```
最新のラベル一覧を取得（npx @trimix/ai-team ticket view <番号>）
if requires_all_of のラベルがすべて除去済み:
    # 除去と付与は必ず単一コマンドで（分けると中間状態が生まれ遷移が壊れる）
    npx @trimix/ai-team ticket edit <番号> --remove-label "<自分のラベル>" --add-label "<次のステップのラベル>"
else:  # 待機パス（相手が未完了）
    npx @trimix/ai-team ticket edit <番号> --remove-label "<自分のラベル>"
    # 競合ウィンドウの解消（スキップ禁止）:
    # 両者がほぼ同時に完了すると互いに待機し合い、どちらも次のラベルを
    # 付与しないサイレント停止が起こり得るため、除去後に必ず再確認する
    最新のラベル一覧を再取得
    if requires_all_of のラベルがすべて除去済み and 次のステップのラベルが未付与:
        npx @trimix/ai-team ticket edit <番号> --add-label "<次のステップのラベル>"
        # ラベル付与は冪等であり、両者が重複して付与しても無害

# 遷移後の検証（必須）
最新のラベル一覧を再取得し、
「自分のラベルが除去済み かつ 次のステップのラベルが付与済み」かを確認する
```

**不整合検知時のリカバリ:**  
遷移後の検証で、次の3条件を**すべて**満たす場合のみ「遷移が途中で中断された状態」と判定してリカバリします。

| # | 条件 |
|---|------|
| 1 | `requires_all_of` に列挙された並列ステップのラベルがすべて除去済み |
| 2 | 次のステップのラベルが付与されていない |
| 3 | ワークフロー上の後続ステップ（次のステップより先のステップ）のラベルがいずれも付与されていない |

条件3は誤発動ガードです。後続ステップのラベルが1つでも付与されていればワークフローは進行中であり、過去のステップのラベルを再付与してはいけません（リカバリ不要）。

3条件を満たす場合のリカバリ手順:

1. `npx @trimix/ai-team ticket edit <番号> --add-label "<次のステップのラベル>"`
2. リカバリした旨を チケットにコメントする  
   （例: `⚠️ ラベル遷移の不整合を検知したため、<次のステップのラベル> を付与してリカバリしました`）

## 委託監視プロトコル（点呼・ウォッチドッグ）

Opus / Sonnet をオーケストレーター（このスキルを実行している主体）として動かす場合、委託したサブエージェントが API エラー等で無音停止しても、モデルの自発的な注意力だけでは検知できません（実測: 2026-07-24 に、API エラーで異常終了したサブエージェント2件に約40分気づけなかった）。この節は、サブエージェント（Task/Agent ツール）へ作業を委託する**すべての**箇所（ステップ6のエージェント実行に限らず、Dispatcher によるサブチケット分解の委託等も含む）に適用します。

**中核メカニズムの要点**: バックグラウンドプロセス（後述の `bin/watchdog.js`）の終了通知は、ハーネス機能でありモデルの注意力に依存しません。これを Opus/Sonnet でも機能する唯一信頼できる「起床経路」として使い、モデル自身が定期的に思い出して確認する方式には依存しません。

> **対象範囲の限定**: 本プロトコルは Claude Code（Opus/Sonnet/Fable）を runtime として動作する場合を対象とします。Grok Build ランタイムでのバックグラウンドプロセス完了通知の挙動は本 Issue の対象外です（未検証）。

### 設定（`.claude/ai-team-config.yml` の `delegation_watchdog`。キー不在時は既定値で後方互換動作）

```yaml
delegation_watchdog:
  stall_threshold_minutes: 10   # heartbeat の5分間隔の義務を2回欠いたら停止を疑う
  max_redelegations: 2          # rework_limit と同じ思想（3回目は人間へエスカレーション）
```

| キー | 既定値（キー不在時） |
|------|----------------------|
| `stall_threshold_minutes` | `10` |
| `max_redelegations` | `2` |

### 委託前手順

1. **作業台帳の作成**: `.claude/delegation-status/issue-<番号>/<task-slug>/` ディレクトリを作成し、`heartbeat.log`（初回は空ファイルで作成可）と `done`（完了マーカー。まだ作らない）のパスを決めます。`<task-slug>` はステップID・エージェント名から機械的に生成します（例: `implementer`、並列時は `reviewer-a` / `reviewer-b`）。
2. **二重委託の照合**: 委託しようとしている対象ファイル・対象範囲が、現在進行中の他タスクの作業台帳（同チケット配下の他 `<task-slug>` ディレクトリ）と重複していないか確認します。重複がある場合は委託前にチケットコメントで注意喚起し、範囲を調整します（インシデント #6: 出力先・削除範囲の明示指定と同じ理由）。
3. **進行中タスク台帳のコメント記録**: 委託内容（担当・対象ファイル・作業ディレクトリ・渡したモデル）をチケットコメントに記録します。
4. **委託先のモデル**: エージェント定義の frontmatter の `model` を、Agent ツールの `model` に渡します（渡さないと、このセッションのモデルで動き、役割別モデルが効きません）。渡したモデルは 3. の記録に書きます。広い探索を Explore に任せるときは、Explore の既定のモデルのまま使います。

### 委託プロンプトの骨組み

委託するプロンプトは、次の骨組みで書きます。資料と指示をタグで分け、長い資料を先に、問い（やること）を最後に置きます。サブエージェントはこのプロンプトしか知らないので、目的・分かっていること・作業場所・完了条件・出力先を省きません（決定: 2026-11-22、Issue #125）。

```
<目的>このステップで何を達成するか（1〜2文）と、その理由</目的>
<分かっていること>チケット番号、前のステップの結論、照合済みのインシデント</分かっていること>
<作業場所>pwd（worktree 方式なら作業ディレクトリの絶対パス）と、作業するブランチ</作業場所>
<資料>エージェント定義・設計コメント・関係ファイルのパス（長いものはここに置く）</資料>
<手順>エージェント定義のどのステップを実行するか</手順>
<完了条件>エージェント定義の「完了条件（exit criteria）」を転記</完了条件>
<出力先>書き込んでよいパスと、完了報告を投稿するチケット</出力先>
（ここに、次の「委託プロンプト必須条項」をそのまま入れる）
```

### 委託プロンプト必須条項（サブエージェントへの指示に必ず含める）

委託するプロンプトには、以下6条項を**そのまま**含めてください（委託先に求める定期報告・点呼への即応・完了の合図を、機械的なハートビートと完了マーカーに接続したものです）。

```
1. 着手時・主要ステップ完了ごと・失敗/ブロッカー発生時（即時）・完了時に報告してください。
   無音の失敗は最悪の事故とみなします。
2. 主要ステップごと（最低5分に1回）に次を実行してください:
   date '+%Y-%m-%dT%H:%M:%S' >> <heartbeat.log の絶対パス>
3. 完了時に <done マーカーの絶対パス> ファイルを作成してから終了してください
   （成功・失敗を問いません。失敗時は理由をファイルに書き込んでください）。
4. STATUS? を受けたら最優先で3行以内（①いまどの段階か ②何ができたか ③詰まっていること）
   + 実測値（ファイル名・行数等）を1つ以上添えて即応してください。
5. 出力先はこの指示で明示されたパスに限ります（範囲外の削除・書き込みは禁止です）。
6. チケットコメント・PR 本文は、1行目・要点1〜3行（実測値のみ）・人への依頼・`⏭️ 次のアクション:` 行
   だけを表示し、それ以外は `<details><summary>詳細（エージェント向けの記録）</summary>` に入れてください
   （`<summary>` の直後と `</details>` の前後に空行。1行目は先頭、`⏭️` 行は `</details>` の外に1つだけ）。
```

### サブエージェント起動と同時にウォッチドッグを起動

サブエージェントを起動したら、**同時に**（起動直後、完了を待たずに）以下をバックグラウンド実行してください。

```bash
node <パッケージルート>/bin/watchdog.js \
  .claude/delegation-status/issue-<番号>/<task-slug>/heartbeat.log \
  --threshold-min <delegation_watchdog.stall_threshold_minutes> \
  --done-marker .claude/delegation-status/issue-<番号>/<task-slug>/done
```

このコマンドはバックグラウンドで実行し、終了時にオーケストレーター（このセッション）へ完了通知が届く実行方式を使ってください。`bin/watchdog.js` は Node 標準のみで動作し、`.claude/delegation-status/` 配下のパスを `lstatSync` でのみ検査します（`readFileSync` は使いません。インシデント #4 教訓15: FIFO 等のプロジェクト側パスは読み込み経路でも封じ込め検査が必要）。

### 起床時の判定手順（watchdog 終了コードで分岐）

`bin/watchdog.js` の終了コードは `0`（完了検出）/ `2`（検査エラー・引数不正）/ `3`（無音検出）です。stdout の1行 JSON（`{"result":"done|stall|error",...}`）も参照してください。

**exit 0（done 検出）= 正常完了:**
- サブエージェントの完了報告（チケットコメント）を確認・検証してから次のステップへ進みます。

**exit 2（検査エラー）:**
- 引数不正または heartbeat/done-marker が通常ファイルでない実体（symlink・FIFO・ディレクトリ等）です。原因をチケットコメントに記録し、watchdog を安全な設定で再起動するか、握りつぶさず人間に確認します。

**exit 3（無音検出）= 停止疑い:**
1. **裏取り（必須）**: `heartbeat.log` と成果物ファイルの `mtime` を実測して確認します（長考中は応答が無くても動いているので、経過時間だけで死亡と判定せず、時刻の実測で裏を取る）。
2. **生存と判断した場合**: watchdog を同じ設定で再起動し、監視を継続します（再委託はしません）。
3. **死亡と判断した場合**:
   - 同一プロンプトに「中断点までの成果物」を補足したプロンプトで**再委託**します。
   - watchdog も同時に再起動します（heartbeat.log は使い回してよい。done マーカーはまだ存在しないため再利用可能）。
   - 再委託回数をチケットコメントで管理します（差し戻し回数のカウント方式と同様、コメント先頭行で数えられる形にしてください）。
4. **再委託回数が `max_redelegations` を超えた場合**: 再委託をやめ、`subagent_stall` として `escalated:human`（human-escalator）へ遷移します。

**すべての検知・再委託・エスカレーションのイベントを、チケットコメントとユーザーへの報告に必ず記録してください**（無音の失敗を作らないため）。

## チケット CLI 失敗時のフォールバック

`npx @trimix/ai-team ticket ...`（github 時は内部の `gh`）が失敗した場合は、以下の手順で対応してください。**失敗を無視して黙って先に進んではいけません。**

**ラベル不存在による `--add-label` 失敗の場合（github のみ）:**  
リトライの前に `gh label create` でラベルを作成してから再実行してください。`ticket_backend: local` ではラベルの事前作成は不要です。

```bash
# github 時のみ: ラベルを作成してからリトライ
gh label create "<ラベル>" --color "<色>" --description "<説明>"
npx @trimix/ai-team ticket edit <番号> --add-label "<ラベル>"
```

**その他の失敗（ネットワーク・ファイル I/O 等）の場合:**

1. **原因を確かめてから、1回だけリトライする**: エラー出力を読み、認証（github 時は `gh auth status`）・ネットワーク・レート制限・ファイルの書き込み権限のどれに当たるかを確かめ、直せるものは直してからリトライします（同じコマンドの再試行に人の承認は要りません。回数は1回のままです）
2. リトライでも失敗した場合は、**実行すべきコマンドをそのままユーザーに提示して停止**する

提示例：

```
⚠️ チケット CLI の実行に失敗しました（1回リトライ済み）。
以下のコマンドを手動で実行してから、/ai-team-resume で再開してください：

npx @trimix/ai-team ticket edit 42 --remove-label "backend:reviewer-a" --add-label "backend:cross-review"
```

ラベル遷移やコメント投稿が完了していない状態で次のステップへ進むと、状態管理が壊れ、`/ai-team-resume` で再開できなくなります。

## 状態記録要件（コメント必須5フィールド）

各エージェントは、自分のステップが完了するたびに以下の**必須5フィールド**を含むコメントを チケットに投稿してください。

| フィールド | 内容 |
|-----------|------|
| 実施内容 | このステップで何を行ったか |
| 成果物 | 作成・変更したファイル・PR・コメント等の一覧 |
| 判断根拠 | 分岐・選択を行った理由と参照したルール・ドキュメント |
| 完了条件チェック | このステップの完了条件（exit criteria）の充足状況 |
| 次のアクション | 次に起動するステップ・付与するラベル（`⏭️ 次のアクション:` 行で明示） |

**目的**: セッションが途中で中断しても、`/ai-team-resume` が**コメント履歴のみ**でワークフローの状態を復元し、続きから再開できる状態を常に保つためです。エージェントの内部状態や会話コンテキストに依存した引き継ぎをしてはいけません。

### コメントの表示構成（折りたたみ）

チケットコメントと PR 本文は、**人が承認判断に必要な情報だけを表示し、それ以外は折りたたみます**（決定: 2026-09-30、#116）。全文を展開すると、コスト増・既存環境への影響・人の対応の要否が埋もれ、何が重要か判断できなくなるためです。折りたたむのは表示だけで、記録の中身（必須5フィールド・計測値・変更ファイル表・判断根拠・完了条件チェック）は削りません。

```
<1行目: 絵文字 担当名: 見出し>            ← 変更しない。必ずコメントの先頭

<要点 1〜3行>                              ← 見出しは付けない

（人への依頼の節がある場合。例: human-escalator の「判断が必要な選択肢」）

<details>
<summary>詳細（エージェント向けの記録）</summary>

## 実施内容
…（必須5フィールドのうち次のアクション以外・計測値・変更ファイル表・判断根拠・完了条件チェック）

</details>

⏭️ 次のアクション: …

（人への依頼の節がある場合。例: pr-creator の承認依頼、human-escalator の「対応完了後の手順」）
```

- **表示したまま残すもの**: ①1行目 ②人が知っておくべき要点1〜3行（判定結果・コストや既存環境への影響・訂正・人の対応の要否） ③`⏭️ 次のアクション:` 行 ④人への依頼の節（承認依頼・エスカレーションの判断依頼など）
- **`<details>` に入れるもの**: 上記以外のすべて。`<summary>` はコメントでは `詳細（エージェント向けの記録）` に固定する
- **空行は3か所で必須**: `<summary>` の直後、`</details>` の直前、`</details>` の直後。無いと GitHub で中の表・リストや直後の行が Markdown として描画されない
- **1行目と `⏭️ 次のアクション:` 行は `<details>` の外に置く**。`<details>` をコメントの先頭に置いてはいけない。`⏭️` 行は `</details>` の外に**1つだけ**置く（`<details>` の中に `⏭️` 行を置かない）。理由は読み手が生テキストを読むため: 差し戻し回数の照合（各コメントの1行目 `split("\n")[0]`）、AI コメントの判定（1行目の先頭の絵文字）、`/ai-team-resume` の状態復元（最後の `⏭️ 次のアクション:` 行）
- **要点行には実測した事実だけを書く**。テンプレートの既定文言（「全件パス」など）を埋めただけの行を表示側に出さない（インシデント #11）。人の対応が無いときは「人の対応は不要」と書く
- **畳まなくてよい短い連絡**: 1行目・要点・人への依頼しか無く、畳む記録が無いコメント（再開の通知・リマインドなど）は、雛形どおりの短い形のままでよい
- **PR 本文**: `## 概要` と `## 承認前に知っておくこと` を表示し、残りは話題ごとの `<details>` に入れる。`<summary>` は内容の名前にする（例: `変更ファイルの内訳`・`設計方針`・`テストとレビューの詳細`）。PR の読み手は人だけなので、コメントと違って固定文言にしない。`**検証**:` 行と `## テスト` には、実行したコマンドと結果だけを書く（CI・リントが無いときは「無し」と書き、代わりに行った確認を書く）

### 引き継ぎ前チェック（各ステップ共通）

次のステップへ引き継ぐ前に、以下を確認してください。

- [ ] 完了コメントに必須5フィールドがすべて含まれている
- [ ] 1行目がコメントの先頭にあり、`⏭️ 次のアクション:` 行が `</details>` の外にある（上記「コメントの表示構成（折りたたみ）」）
- [ ] `npx @trimix/ai-team ticket view <番号>` で完了コメントが実際に投稿されている
- [ ] 同コマンドで labels が期待どおり遷移している（自分のラベル除去・次のラベル付与）

## 差し戻し上限（rework_limit）

workflow.yml に `rework_limit` が設定されている場合、同一チケットでの差し戻し（不合格による戻し）回数に上限が課されます。**上限値は workflow.yml の `rework_limit` が正**です（以下は `rework_limit: 2` の場合の説明）。

### 差し戻しコメントの先頭行規約

差し戻し（不合格）コメントの**先頭行**は、必ず次の形式で記述します。

```
❌ <エージェント名>: 差し戻し（差し戻し回数: n/2）
```

### カウント方法（先頭行のみ照合）

reviewer（クロスレビューを含む）は不合格判定を出す前に、以下のコマンドで**過去の差し戻しコメント数を数えて**ください。コメントの先頭行のみを照合するため、本文中の引用・言及による偽陽性は発生しません。

```bash
gh api "repos/<owner>/<repo>/issues/<番号>/comments" --paginate \
  --jq '.[].body | split("\n")[0]' | grep -cE '^❌ .+: 差し戻し' || true
```

- カウント **n < 2**（`rework_limit` 未満）→ 差し戻し可。通常どおり `on_rework` の差し戻し先へ戻す
- カウント **n ≥ 2**（`rework_limit` 以上）→ 差し戻しせず `escalated:human` へ遷移する（human-escalator を起動し、差し戻しが上限に達した旨と争点をエスカレーションコメントに記録する）

同じ指摘での差し戻しが繰り返される場合、要件の曖昧さや設計上の対立などAIだけでは解決できない問題が背景にあることが多いためです。

## インシデントの即時記録と再照合（発火点: 差し戻し・エスカレーション・再実装）

同一クラスの失敗が同一チケット内で繰り返される事故（インシデント #4 / Issue #86）を防ぐため、**失敗が発生したその時点で**インシデントを記録し、**再実装の担当を起動する前に**記録済みの再発防止策を照合します。

この記録・照合は、各チームのリーダーエージェント定義に書くだけでは確実には発火しません。**多くのチームでは** workflow.yml の差し戻し（`on_rework`）・エスカレーション（`on_escalation` / `rework_limit` 超過）の**遷移先にリーダーが現れない**ためです（backend の `on_rework.next` は `implementer`、`on_escalation.next` は `human-escalator`。いずれもリーダー = `tech-lead` を経由しません。frontend の差し戻し先は `developer`、content・sns の差し戻し先は `researcher` / `writer`）。ただし **`infra` は例外**で、`on_rework.next` が `infra-lead-analysis`＝リーダー `infra-lead` へ戻ります。本スキルの発火点は特定のエージェントではなく**遷移種別**（`on_rework` / `on_escalation` / `rework_limit` 超過）をトリガーにしているため、遷移先がリーダーか否かに関わらず全チームで発火します（infra でも本スキルが発火します）。infra では本スキルの照合と `infra-lead` 定義側の再照合とで二重になりますが、既に規定した dedup（`.claude/incidents/index.yml` を先に照合してから記録する）により重複記録は起きません。これらの遷移を実際にオーケストレートするのは本スキルであるため、以下の3つの発火点での記録・照合は**本スキルの責務**とします。

> **記録の重複回避（全発火点共通）:** 記録の前に `.claude/incidents/index.yml` を読み、当該チケット番号（`issue`）と事象（差し戻し/エスカレーション）に対応するエントリが既にあるか照合します。既にリーダーや human-escalator が記録済みなら新規レポートは作らず、既存エントリの不足（`keywords`・再発防止策等）を補うにとどめます（Contributor のクローズ時検証と同じ dedup 方針）。記録書式は `.claude/agents/contributor.md` の「インシデントレポートフォーマット」、`index.yml` は既存スキーマ（`id` は既存最大+1・`date`・`file`・`title`・`severity`・`teams`・`issue`・`keywords`）に従います。`.claude/incidents/index.yml` が読み込めない場合は記録をスキップした旨を差し戻し/エスカレーションコメントに残し、握りつぶしません。

### 発火点1: 差し戻しコメントを投稿する直前（on_rework）

reviewer（またはクロスレビュー）の判定を受けて差し戻しコメント（先頭行 `❌ <エージェント名>: 差し戻し（差し戻し回数: n/…）`）を投稿する**直前に**、その差し戻しの原因・争点を `.claude/incidents/` に記録し `index.yml` に登録します。Contributor のクローズ処理を待ちません（待つと同一チケット内の次の再実装で教訓が参照されない＝インシデント #4 の副次原因）。記録した参照パスは差し戻しコメントにも併記します。

### 発火点2: on_rework の遷移先エージェントを起動する前（再実装）

差し戻し後、`on_rework.next` のエージェント（backend では `implementer`、frontend では `developer`、sns では `researcher`/`writer` 等）を起動する**前に**、`.claude/incidents/index.yml` を照合します。当該チケットに関連する再発防止策（発火点1 で今記録したものを含む）を、起動する担当への**作業指示に明記して反映してから**起動します。前回の教訓を反映しないまま再実装を指示すると、同一クラスの欠陥を繰り返します（インシデント #4 の根本原因）。着手時の1回きりの照合では発火しないため、**差し戻しのたびに**照合します。

### 発火点3: escalated:human へ遷移する時点（on_escalation / rework_limit 超過）

`on_escalation.next: human-escalator` への遷移時、または `rework_limit` 超過で差し戻しをやめて `escalated:human` へ移す時点で、その原因と経緯を `.claude/incidents/` に記録し `index.yml` に登録します。エスカレーション実務（コメント・ラベル・アサイン）は human-escalator が担い、human-escalator 定義（`.claude/agents/human-escalator.md`）にも同じ記録責務を持たせています。本スキルが先に記録済みなら human-escalator は dedup により検証にとどめます（逆も同様）。

## ワークフロー停止条件

以下のいずれかに該当する場合はワークフローを停止し、ユーザーに状況を報告してください：

- `escalated:human` ラベルが付与された（人間の判断が必要）
  → エスカレーションコメントに再開手順を案内し停止。人間の対応後に `/ai-team-resume` で再開。
- PR の承認・マージが必要になった（人が範囲を明示して代行を任せた場合だけ、`.claude/escalation-rules.yml` の `merge_approval` の条件を実測してから代行し、代行したことと根拠をチケットコメントに残して先へ進む）
- セキュリティレビューで重大リスクが発見された
- エスカレーション条件（`.claude/escalation-rules.yml`）に該当した
- チケットがクローズされた（Contributor が完了処理済み）
- 「書き込みの同意」が得られなかった（ここまでに分かったことをターミナルに示して停止）
