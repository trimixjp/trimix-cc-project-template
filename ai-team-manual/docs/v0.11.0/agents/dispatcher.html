Dispatcher エージェント

Dispatcher エージェント

Dispatcher は、大きな作業要件（Epic Issue）を受け取り、各チームが実行できる単位のタスクに分解して割り当てる「仕事の振り分け役」です。このエージェントが動くことで、複雑な要件でも適切なチームへスムーズに引き継がれます。

> 定義場所: .claude/agents/dispatcher.md

何をするエージェントか

Dispatcher は次の 2 つのことを行います。

  1. Epic の内容を読み解く — Issue に書かれた要件を解析し、どのチームが関係するかを判断する
  2. タスクを振り分ける — 単一チームで完結するならそのままディスパッチし、複数チームにまたがるなら Sub Issue を生成して各チームへ割り当てる

実行計画（フェーズ・依存関係）は必ず Epic Issue のコメントとして記録されるため、人間も含めた全員がどの順序で何が進んでいるかを把握できます。

起動条件

条件説明
epic ラベル付き Issue の作成・更新新しい Epic が登録されたとき
dispatcher ラベルの付与既存 Issue を Dispatcher に再処理させたいとき
dispatcher:run ラベルの手動付与人間や他のエージェントが明示的に起動を要求したとき

動作フロー

flowchart TD A[Epic Issue が登録される] --> B[🔍 分析開始コメントを投稿] B --> C{複数チームにまたがるか?} C -- 単一チームで完結 --> D[ケースA: Epic に担当ラベルを直接付与] C -- 複数チームにまたがる --> E[ケースB: チームごとに Sub Issue を生成] D --> F[📋 ディスパッチ完了コメントを投稿] E --> G[Sub Issue を Epic にリンク] G --> H[実行フェーズ・依存関係を Epic コメントに記録] H --> F F --> I[各チームのリーダーエージェントへ引き継ぎ]

ケースA: 単一チームで完結する場合

作業がひとつのチームの範囲に収まる場合は、Sub Issue を新たに作らず Epic Issue 本体に担当チームのラベルを付与して直接ディスパッチします。

典型的な判断基準

チーム担当の目安
バックエンドチーム（tech-lead）コード実装・API 変更・テスト追加が主体
コンテンツチーム（editor-in-chief）ドキュメント・仕様書・コンテンツ作成が主体
インフラチーム（infra-engineer）インフラ構成・CI/CD・環境設定変更が主体

ケースB: 複数チームにまたがる場合

作業が複数のチームに関わる場合は、チームごとに Sub Issue を 1 件ずつ生成します。各 Sub Issue には担当チームのラベルが付与され、対応するチームリーダーエージェントが自動的に起動します。

Sub Issue 間に依存関係がある場合（例: インフラ設定が完了してからバックエンド実装を開始するなど）は、フェーズを分けた実行計画がコメントに記録されます。

sequenceDiagram actor 人間 participant Dispatcher participant GitHub Issues 人間->>GitHub Issues: Epic Issue を登録 GitHub Issues->>Dispatcher: epic ラベルを検知して起動 Dispatcher->>GitHub Issues: 🔍 分析開始コメントを投稿 Dispatcher->>Dispatcher: 要件を解析・チーム境界を判定 Dispatcher->>GitHub Issues: Sub Issue #A を生成（チームA担当） Dispatcher->>GitHub Issues: Sub Issue #B を生成（チームB担当） Dispatcher->>GitHub Issues: 📋 Sub Issue 分解完了コメントを投稿
（フェーズ・依存関係を含む） GitHub Issues-->>チームA: backend:tech-lead ラベルで起動 GitHub Issues-->>チームB: infra:engineer ラベルで起動

GitHub コメントの形式

分析開始時

Epic Issue に次のコメントが投稿されます。

🔍 Dispatcher: 分析を開始します

対象Issue: #<番号> <タイトル>
分析中のシステム領域: <フロントエンド / バックエンド / インフラ / ドキュメント 等>

ケースA 完了時（単一チームへのディスパッチ）

📋 Dispatcher: 単一チームにディスパッチ完了

担当チーム: <チーム名>
担当リーダー: <リーダーエージェント名>

ケースB 完了時（複数チームへの分解）

📋 Dispatcher: Sub Issue 分解完了

生成した Sub Issue:
- #<番号> [tech-lead] <タイトル>
- #<番号> [infra-engineer] <タイトル>
- #<番号> [editor-in-chief] <タイトル>

実行フェーズ: <フェーズ数>
並列実行可能な Sub Issue: <番号リスト>
依存関係あり（順序制約）: <番号 → 番号>

判断不能時（エスカレーション前）

⚠️ Dispatcher: 判断不能項目あり

以下の項目についてチームアサインの判断ができませんでした。
human-escalator を呼び出して人間に確認を求めます。

判断不能の理由:
- （理由を具体的に記述）

エスカレーション

以下のケースでは Dispatcher は自分で判断せず、Human-Escalator を呼び出して人間に確認を求めます。

  • Epic の要件が矛盾しており、分解方針を決定できない
  • 既存のチームマッピングに該当しない新しい領域の作業が含まれる
  • セキュリティや法的判断を伴うチームアサインが必要
  • escalation-rules.yml のエスカレーショントリガーに該当する事象が発生した

重要な原則

  • Dispatcher 自身はコードを書かず、実装判断も行いません
  • Sub Issue のタイトル・本文には、担当リーダーが作業を開始できる十分な情報が含まれます
  • 依存関係を明確にせずに Sub Issue を生成することはありません
  • 1 つの Sub Issue の担当チームは必ず 1 つです
